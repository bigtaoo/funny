## 48. 竖屏批量修：一套自动巡检 + 它查出来的七处重叠（2026-09-11）

**起因**：日常在电脑上开发＝横屏，竖屏问题只能靠人肉在手机上一屏一屏截图报过来，于是「横屏的大部分修完了，竖屏还是到处叠在一起」。

**先做工具**：`client/test/browser/portraitLayout.spec.ts` + `lib/layoutAudit.ts`（说明见 [`claudedocs/client-testing.md`](../../claudedocs/client-testing.md)「竖屏几何巡检」）。真 Chromium 走 **21 个场景 × 3 个竖屏尺寸**（390×844 / 360×640 / 768×1024），在页面里遍历真实 PIXI 显示树判 6 类问题，并给每站落一张 PNG。**这一层不可省**：headless `test:ui` 的 `measureText` 桩是「字符数 × 7px、跟字号无关」，而竖屏问题清一色是宽度不够导致的折行/溢出——在那层结构性复现不了（`titlesPortraitOverlap.ui.ts` 头注释早就写过同一件事）。

**首轮查出 7 处，全部已修**：

| # | 症状 | 真因 |

**同时给巡检器定的两条精度规则**（否则它会变成噪音源）：
- **框是「画在文字下面、且能整个装下它」的那个盒子**。取「最紧的那个」会把装饰当框——大厅主按钮里那对交叉铅笔就是一张比按钮小的 sprite，按最紧取法，按钮上每个字都算溢出。
- **只有画在文字之后的实心矩形算「盖住」**。`Graphics` 的 bounds 不等于它涂到的像素：头像那圈 rim 是一张透明 PNG sprite、描边 `Graphics` 也只画边，把它们当遮盖物，头像里的字母全成了「被盖住」。放弃 z 序（想顺带抓「条画在标题下面」那种）会让每个普通按钮都中招，实测噪音从 9 条涨到 46 条，已回退。
- 引导气泡这类**本来就该盖在别人身上**的层，由产品侧显式标记：`GuideOverlay` 的根容器 `name = 'overlay:guide'`，巡检器只在同一层内互比。

**收尾状态**：三个尺寸全绿（`npm run test:portrait`）。**尚未处理**：竖屏下 `FS.micro`（11 设计 px）在 390 宽的手机上只有 ~4 CSS px——防御编辑器页脚、主城资源行那类小字确实小到读不了，但这是字号表和竖屏缩放比的系统性问题，不是重叠，另案。

## 49. 竖屏第二轮：可读性下限、主城版面、巡检扩面到 32 站 × 6 尺寸（2026-09-11）

接着 §48 那条「另案」办。四件事一次做完：**① 字号可读性下限**（§48 收尾那条）、**② 主城竖屏版面**（巡检看不见的那种不对劲）、**③ 巡检扩面**（战斗 HUD / 结算页 / 各种弹窗以前一站都没走到）、**④ 同一套巡检用到横屏**。

### 49.1 可读性下限：设计 px 不是屏幕 px（`render/fontScale.ts`）

**根因一句话**：竖屏设计宽度钉死 1080，390 宽的 iPhone 于是整屏按 **0.36×** 渲染，360 宽的安卓 0.33×。`FS.micro` 的 11 设计 px 落到屏上就是 **4 CSS px**。这不是「某处字号选小了」，是**字号表用的单位和玩家眼睛用的单位之间差了 2.8 倍**，所以修法也不该是逐处把 `FS.micro` 换成 `FS.tiny`。

**做法**：`FS` 的十个 token 全部改成 getter，读的时候抬到一条**由当前设计缩放比反推的下限**上：

```
floor(scale) = clamp(向上吸附到档位(MIN_LEGIBLE_CSS_PX / scale), micro, FLOOR_CAP)
MIN_LEGIBLE_CSS_PX = 7    FLOOR_CAP = FS.bodyLg (20)
```

| 视口 | 缩放 | 下限 | 效果 |
|---|---|---|---|
| 390×844 竖 | 0.361 | **20** | micro/tiny/small/body 全抬到 20（7.2 CSS px）；label 以上不动 |
| 360×640 竖 | 0.333 | **20**（撞上限） | 6.7 CSS px —— 见下方「没买到什么」 |
| 768×1024 竖 | 0.533 | **16** | micro/tiny 抬到 16（8.5 CSS px） |
| 844×390 横 | 0.361 | **20** | 手机横屏和竖屏是同一道算术 |
| 1366×768 横 | 0.711 | 11（= 不抬） | 桌面开发环境一个像素不动 |

三个刻意的设计点：

- **改 `FS` 而不是改文字工厂**。下限如果加在 `txt()` 里，字变大了、但它旁边那行 `y += FS.small + 6` 的排版算术**还按旧数**——正是行距压穿的配方。改成 getter，两边读到的是同一个数，~590 个调用点一个都不用动。
- **下限本身是个档位**（向上吸附），不是一个随缩放漂移的浮点数。被抬起来的 `micro` 和场景本来就写 `small` 的地方长得一模一样。
- **封顶在 `bodyLg`**。要让 390 宽手机上的小字真到 9–10 CSS px，下限得是 ~25 设计 px，那已经**高过 `FS.label`**：从小字到分区标题会全部塌成一个字号，整套竖屏 UI 得围着它重排一遍。封顶把返工圈在「本来就短的标签」上。
- **只看缩放比、不看朝向**。手机横过来照样 0.36×，同一套下限；桌面横屏问都不用问。

**没买到什么（老实话）**：360 宽的机器被封顶挡在 6.7 CSS px，还是低于 7 的目标；`body` 以上的档位在手机上依旧偏小（`FS.body` 18 → 6.5 CSS px，抬到 20 也才 7.2）。**真正的解法是竖屏的设计宽度**（1080 对 390 的屏太宽），那是另一件大得多的事，不在本轮。

**门禁**：巡检器的 `tiny` 判据改成**「有效字号 < 该视口的 `fontFloorDesignPx(scale)`」**，两边共用同一个函数（spec 直接 `import` `src/render/fontScale`，它零依赖）。

判据同时从「量 ink 盒高」换成「读字号本身」，因为盒高根本量不准：**烘焙标签（`cachedTxt`/`numTxt` 的 Sprite）报的是裁紧的字形盒（≈ 字号的 0.96 倍），活的 `PIXI.Text` 报的是行盒（≈1.35 倍）**——同一条「盒高」门槛要么放过被缩到一半的字，要么冤枉正常的字。活 Text 读 `style.fontSize`，烘焙标签读 `render/fastText.ts` 新盖的 `fsPx`（那个模块本来就为这套巡检往 `name` 上盖 `txt:` 前缀，多盖一个字号是同一笔账）。再乘上它头上累计的局部缩放 = 有效字号。`tiny` 条目的 `b` 字段现在直接写诊断：`font=24 scale=0.68`——「太小了」本身不可行动，「谁把它缩的」才是。

### 49.3 巡检扩面：22 → 32 站，含战斗 HUD、结算页和五个弹窗

旧表只走到「大厅一跳」和少数两跳。扩的依据就是报告自己记的 `cbKeys`（每站把 `state.<screen>Cb` 的键列出来——那就是导航图），新增：

- **回调可达的**：`mail` / `battlePass`（挂在抽卡屏和商店屏的 bag 上，不在大厅）/ `feedback`、`family`、`sect`（后三个这账号确实没有，按 `gated` 记为跳过）。
- **战斗**：`onStartGame('AI')` → `game`。这是唯一一站离开菜单外壳——战斗 HUD 直接由 `ILayout` 排版，是竖屏唯一能以「菜单场景不会出现的方式」坏掉的地方。
- **结算页**：`game` 的 bag 只有 `onGameEnd` 和 `onExitToLobby`，于是**直接把渲染器本来会递给它的那份收尾数据递给它**（`onGameEnd(0, [stats, stats])`，`PlayerStats` 照抄 `server/engine/src/types/runtime.ts` 的字段）。打完一局 AI 要几分钟，而这一站要审的是「一屏数字的排版」——数字哪来的不影响。
- **弹窗：回调够不着，只能点。** 弹窗是场景内部的命中区打开的，永远不会是一个 screen，也就没有任何回调可调。新增 `tapLabel(page, 文字)`：在真实显示树里按文字找到那个标签、点它的中心——真事件、真 InputManager、真命中表，跟玩家的手指走同一条路。于是有了 5 站：`cardRoster+detail`、`equipment+craft`、`gacha+draw`、`city+buildDetail`、`city+trainModal`。`Stop.as` 给这类站单独的报告名（`state.screen` 还是底下那个场景，两站会互相覆盖报告和截图）。
  > 点的尽量是 **UI 字符串**而不是内容名（用 `Power` 这个统计标签进英雄详情，而不是「李闯」），免得表依赖新号发哪几张卡。

### 49.4 六个尺寸：横屏走的是同一套

`VIEWPORTS` 加两行手机横屏/平板横屏 + 一行 1366×768 桌面。为此把设计矩形从常量改成**按视口算**（`designBox`：两种朝向都把短边钉在 1080、长边跟着长宽比走，竖屏不短于 1920，横屏在 1920–2592 之间），`tiny` 门槛同样按视口算。桌面那行的作用是「地板」——它的 0.71× 根本不触发可读性下限，所以它报出来的任何东西都是纯排版 bug，不是缩放假象。

跑完六个尺寸约 25 分钟（单个 `--grep <名字>` 约 3 分钟），per-test 超时从 5 分钟提到 10 分钟。

### 49.5 下限带出来的 7 处返工

抬字号必然撑破一些盒子。全部是巡检报出来的，按「为什么坏」分两类：

**A. 字号变大、盒子/行距没跟着（4 处，纯下限的锅）**

| 位置 | 症状 | 修法 |
|---|---|---|
| 主城建筑详情弹窗 | 「→ Lv.2 / 消耗 / 时长」三行互相压穿 | 行距从字面量 16 改 `max(16, FS.tiny×1.25)`，面板高同源；横屏取到 16，一像素不动 |
| 主城训练弹窗 | 队列状态行 456 设计 px > 340 的面板，跑出屏幕 | 折行，且**先量后定面板高**（面板先画，行数悄悄变 2 会从底下漏出去） |
| 英雄详情弹窗 | 「攻城: 0（每 60 兵 8）」越过面板右边 | 折行到 `statMaxW`（等级星本来就按这个宽度排） |
| 英雄列表卡名 | 名字被缩到 0.84（16.8 设计 px）还顶到卡边 | 竖屏的目标卡宽 300 → **480**（= 2 列）。反直觉但对：竖屏卡里那张肖像框宽度是**卡高**推出来的定值 177，卡宽多出来的每一像素都进信息栏，而信息栏才是要装下名字的那个 |

**B. 「装不下就整组缩」把下限吃掉（3 处，老问题被门禁照出来）**

`group.scale.set(可用宽 / 需要宽)` 这个写法在下限面前必然破功：它把刚保证过的字号乘上一个任意浮点。新增 `fitFont(size, need, avail)`——**改字号而不是缩已经画好的组**，沿档位表往下走、停在下限（UI 字体是等宽的，宽度对字号线性，所以 `size × avail/need` 就是该用的字号，不用迭代）。

| 位置 | 症状 | 修法 |
|---|---|---|
| 图鉴「类型 · 费用」行 | 24px 被缩到 0.68 = 16.4 | 三级降级再兜底：先 `fitFont` 降档 → 再**丢图标**（图标本就是词前面的提示，不是词的替代）→ 最后才缩 |
| 图鉴属性 chips | 缩到 0.80 = 19.3 | 竖屏图鉴改**一行一张卡**（原来两列，信息栏只剩 245 设计 px；插图是「边长 = 卡高」的正方形，卡宽减半全砍在信息栏上）。横屏仍两列 |
| 世界地图兵力读数 | 「5000/5000」缩到 0.71 = 19.7 | 两格从 50/50 改 **62/38**（「5000/5000」九个字符 vs 「11」两个），并用 `fitFont` 定字号 |

另有一处不是下限的锅、而是扩面照出来的老账：**战令每一行的「×N」和「已领取/未解锁」画在一起**——奖励组按整卡居中、状态标签钉右下角，两者互不知情。改成状态标签先画、把自己的宽度报给奖励组当预留（同 §48 第 6 条主城标题栏那招）。

**C. 按钮标签这一族（`ui/widgets/buttonLabel.ts`，全游戏 96 个调用点的唯一出口）**

它本来就有一条「装不下就丢图标」的规矩（`minFit`，默认 0.82 —— 2026-09-05 那轮 96 处按钮前置图标全量接线时的结论：**「放不下就丢图标」才是能无脑铺开的前提**）。下限来了以后这条规矩有两个洞，各由一个视口照出来：

- **阈值是猜的，下限是量的**：平板上防御编辑器 70 px 宽的页脚按钮需要缩到 **0.89**——过了 0.82 的槛，于是图标留着、`Clear` 被缩到 14.2 设计 px，低于该视口 16 的下限。判据补成 `fit < minFit || fit * size < 下限`：丢掉图标后标签原尺寸就放得下。
- **竖排（`stack`）那条路根本没有降级**：大厅侧边栏是正方形格子、图标在上文字在下，字号又是格子推出来的（0.30×），于是 `Feedback` 八个字符在**任何视口**下都是格宽的 **1.44 倍**——这条路一直在缩它，桌面上缩到 0.61（28px → 17，够读）就是它本来的样子。补成竖排的同族降级：**缩完低于下限时只画图标**——判据是下限而不是「放不下」，所以桌面/平板一个像素不动，只有 0.36× 的手机横屏换成图标；图标本来就是目的地自己的那枚（batch 5/6 美术），比一个糊成灰条的词值钱，徽标层照常标状态。
  > 中途写错过一版：判据写成「放不下就只画图标」，而这条路**每个视口都放不下**，等于把桌面大厅侧栏的五个词全删了。门禁抓不到这种（少画文字永远不会触发文字类判据），是对着「桌面上这条改动应该是 no-op」这个预期反推出来的。

三处 `fitFont` 的调用（上一节 B）也一并改成**只在「缩下去会破下限」时才降档**，不是无脑先降。两种降级不可互换，而且既有那条是刻意的：桌面窗口的下限就是原始的 `FS.micro`，任何缩放都破不了，于是这条改动在桌面**一个像素都不动**。

**D. `FS` 改成 getter 之后新出现的一类 bug：模块级常量会把下限冻住**

`const TEXT_STYLE = { fontSize: FS.tiny }` 这种写法现在是错的——模块初始化发生在 **import 时**，比 `ScalingManager` 算出缩放比还早，于是那份拷贝永远钉在未抬升的表上。全仓库有四处（`HUDView.ts` 两个样式常量、`WorldMapPanels/spec.ts` 两个字号常量），其中 `PANEL_BTN_FONT` 是真的在竖屏上少了 2 px（另外三处取的档位本来就在封顶之上，冻了也看不出来——**这类才是隐患**）。四处全改成函数，规矩写进 `fontScale.ts` 的 `FS` 注释里。函数体内的局部拷贝没问题：场景是在缩放比确定之后才构建的。

### 50.2 seed 为什么必须由 spec 在登录之后调用

`client/test/browser/lib/seed.ts` + `seedFixtures.ts`：直接往 docker 栈的 mongo 写，
`docker exec -i nw-local-mongo sh -c 'cat > /tmp/... && mongosh --file ...'`。

- **不走 UI**：40 人家族要 40 个真玩家、Top-100 要 100 个上榜号，UI 根本产不出来；能产的也要按站按
  视口各花几分钟。
- **不能预先写死**：socialsvc 只存 accountId，显示名是读的时候实时问 metaserver 的；家族/宗门的
  每一处权限判断都比 `leaderId`。所以成员必须是**真账号**、族长必须是**浏览器当次登录的那个号**
  ——而那是 `registerAndEnterLobby` 几秒钟前刚注册的随机号。**预先写好的 seed 不可能知道它。**
- **两段**：账号侧（卡/装备/邮件/好友/家族/拍卖/排行榜）在登录后立刻跑；世界侧（五队满编、
  行军/占领/驻扎/被围攻、宗门、世界频道）必须等 `joinWorld` 建出 `PlayerWorldDoc` 之后——所以
  spec 先走一趟世界地图，回大厅，再喂第二段。

**踩到的**：`mongosh` 直接吃 stdin 是 REPL——提示符 `rs0 [direct: primary] db>` 会跟脚本输出印在
同一行，而且逐行求值，多行 `function`/`if` 全看它的续行判断。改成 `sh -c 'cat > 文件 && mongosh
--file'`，多花一个进程换回正常脚本语义。结果行靠 `@@NWSEED@@` 前缀认，不靠行号。

**踩到的（二）**：`TileDoc._id` 已经是全限定的 `worldId:x:y`，`mainBaseTile` 就是一个 tile id，
不是 `x,y`。第一版按 `x,y` 拼、再自己前缀 worldId，写出来的行军/占领全落在不存在的格子上。

**内容的取值原则**：每个值都取**真实的最坏情况**——名字取到 `MAX_DISPLAY_NAME_LEN`(24) / 家族名取到
`ORG_NAME_WIDTH_MAX`(12 显示宽 = 6 个全角字)、金币七位、家族满 40 人、邮件 24 封（含 80 字上限的
标题 + 1200 字正文 + 四位数附件）、拍卖 44 条（跨页，混固定价/竞价）、排行榜 120 人四位数分档。

### 50.4 三语：locale 是视口矩阵的一列，不是一个乘数

`initI18n` 在**任何场景构建之前**读 `localStorage['nw_locale']`，所以只能用
`context.addInitScript` 在首次导航前塞，不能事后去设置页点。此前每轮跑的都是 Chromium 自己的
`en-US` —— 也就是说**德语和中文从来没被门禁跑过**。

三语 × 六视口 = 75 分钟，太贵。改成**矩阵加四行**：德语和中文只上两台手机（390×844 / 360×640）。
德语是逐词最长的那门（撑破按钮的是它），中文是全角、且没有空格可供折行（是另一类失败）；
四个更宽的视口在英语下本来就有余量，多出来的字符吃得下。

连带的必然改动：`{tap: '文字'}` 这种站点在三语下会找不到标签，全部改成
**`{tap: <TranslationKey>}`**，由 spec 自己按该视口的 locale 查字典（直接 import
`src/i18n/locales/*`，纯数据、零运行时依赖），带 `{cost}` 占位符的取 `{` 之前的字面前缀。
另加一个 `{tapText}` 形式，只允许用于**本套件自己写进数据库的字符串**（那封 `Kampfbericht #1001`
邮件），因为它不依赖「这个号恰好发到哪几张卡」。

  数字在比赛结束那一刻就定死了。
- **`result+extreme`** 保留一份合成的极值（七位伤害、五种兵种的击杀分布）。**录制的那份是真实的，
  真实就意味着它不极端**，两者不能互相替代。

### 50.6 微信入口：先纠正一个前提，再说能做什么

**`entries/wechat-e2e.ts` 不是 `web-e2e` 的孪生，也没有 `__nwE2E`。** 它的文件头这么自称，但它
实际做的只有一件事：构造 `WechatAudioBus`、在 SFX 总线上挂表、逐个 cue 量交付峰值，写一份 JSON 到
`USER_DATA_PATH`。**它不调 `startApp`、不建 PIXI、不挂任何 state/app 出口**，`wechat-probe.ts` 同理
（它只采宿主表面）。所以「把同一张 STOPS 表接上去」目前**没有可接的接口**。

**`claudedocs/client-testing.md` 第 284 行指的那条路（minium / 小程序自动化 SDK）是已经被证伪的死
路**，证据就写在 `wechat-e2e.ts` 自己的文件头里（2026-08-31 实测）：`miniprogram-automator` 能连上
socket，但每一个 `evaluate` / `callWxMethod` 都**永久挂起**——小游戏没有 appservice 供这些命令抵达。
这一条要从那份文档里改掉，别让下一个人再去试一次。

**因此真正可行的形状是「探针入口」，不是「外部自动化」**：一个 `build:wechat-*` 入口，在包内自己
启动游戏、自己走站、自己跑 `layoutAudit`、把报告写进 `USER_DATA_PATH`（开发者工具模拟器下那是本机
真实目录，会话能直接读）。这正是现有两个探针入口的形状。要做的前置：把 `instrumentViews` 从
`entries/web-e2e.ts` 抽成共享模块、把 `layoutAudit.ts` 从 `test/` 挪进能被打包的位置、给包内的走站
逻辑一份不依赖 Playwright 的实现。**本轮没做。**

**本轮做了的是那件更要紧、也更便宜的**：`src/render/textMetricsProbe.ts`——量
`ctx.measureText` 在这个运行时上到底给什么。理由是全仓库每个文字样式都写
`fontFamily: 'monospace'`，而 §49 的两条结论都压在它身上：`fitFont` 一次除法算出「装得下的字号」
只在「等宽字体宽度随字号线性」时成立，可读性下限则是一句关于「一个字最后有多大」的断言。小游戏
运行时没有 DOM、canvas 来自 `wx.createCanvas()`、`'monospace'` 由手机自己解析（很多安卓机对 CJK
给不出等宽面）。**同一个函数**跑两边——`wechat-probe.ts` 里喂 `wx.createCanvas()`，
`test/browser/textMetrics.spec.ts` 里喂 `document.createElement('canvas')`——因为要的是**差值**，
两个数必须由同一份源码产出。Chrome 那侧断言的是两条真正被依赖的性质（每字advance 与字号成正比、
`M` 和 `i` 等宽），不钉具体像素（那是 CI 镜像装了什么字体的性质，会为错误的理由变红）。

### 50.8 最贵的一课：**seed 的数值必须是游戏自己能产生的数值**

`seedFixtures.ts` 的文件头第一句写的就是「每个值都取真实的最坏情况，而最坏情况必须是真的」。
2026-09-12 单视口第一次真跑下来 105 条 finding，**逐条对回服务端常量之后，其中 60 条是在量这份
fixture、不是在量排版**：

| 字段 | seed 写的 | 游戏的上限 | 权威 |
|---|---|---|---|
| 装备词条 id | `p_crit` / `p_def` | 这两个 id 不存在（未知 id 回落成 `p_def +2673` 原样打印） | `SUB_AFFIX_POOL` |
| 装备词条数 | 固定 4 条 | 0/1/2 条，由稀有度定 | `CRAFT_SUB_AFFIX_COUNT` |
| 主词条值 | 存 8630 | **存 base（8/10/6），屏幕自己乘 `enhanceMultiplier`**，+9 也就是两位数 | `MAIN_AFFIX_BY_SLOT` × `ENHANCE_LEVEL_MULTIPLIER` |
| 卡等级 | 60 | 9 | `MAX_CARD_LEVEL` |
| 单卡兵力 | 24800 | 600（李闯）/ 300 | `cardTroopCap` |
| 兵力池 / 上限 | 1482600 / 1600000 | 20000 | `troopCapFor({drillYard:10})` |
| 建筑等级 | 到 20 | 10 | `BUILDING_MAX_LEVEL = DESK_MAX_LEVEL` |
| 资源 | 842 万 | 60 万 | `RESOURCE_CAP × (1 + cabinet×0.20)` |
| 每小时产出 | 12.8 万 | 每格 `100 × level` | `RESOURCE_YIELD_BASE` |
| 地块驻军 | 48200 | 500 起（`npcGarrison` = 120×level 托底） | `GARRISON_PER_TILE` |
| 行军兵力 | 148200 | 20000 | `satchelCarryCapFor` |
| 邮件标题 | `.slice(0, 40)`，而源串本身只有 36 字 | **80 字**（全角即 160 显示宽） | `MAIL_SUBJECT_MAX` |

（`Troops 1500/1500`、`Crit Damage +30%`、`Health +50%`）。

**规矩**：往 seed 里写一个数之前，先找到定义它上限的那个常量，并把常量名写在注释里。找不到上限的字段
（家族繁荣度一类）可以估，但要在注释里说明它是估的。

#### `drawButtonLabel`：补上那个洞，并且补的是**两个**洞

真正改完是两条：

1. **两行分支**。触发条件是「**一行装不下且会破下限**」——精确地说是 `min(1, fitW/text.width) * size <

2. **`scale.set` 一律夹在下限上**（solo 分支和组分支各一处）。夹住之后放不下就**溢出**，不再缩。

   填充盖在字的最后一排像素上。`covered` 的面积占比够不到阈值，所以**九个视口的绿都没拦住它**——
   缩写后的德语和英语（`0T 9h 59m 24s` / `0d 9h 59m 24s`）等长，也就是说**英语一直是同样被切的**，
   只是没人去看。修法是 `AUC_CELL_H` 180 → 200：
   格子是上对齐的，按钮之上的一切原地不动，20 px 正好是量出来的差额。
2. **主城建造队列的表头和条目粘成一串**：`Bauwarteschlange` 16 个字符，写死的 `cx0 + 195` 起点被它
   吃掉 12 px，屏幕上读作 `BauwarteschlangeStadtmauer Lv.10 · …`。改成按表头**实测宽度**起排。

#### 而抬高 `AUC_CELL_H` 又炸出了第四条——**一条一直在那儿的 cull bug**

十行矩阵跑完，`narrow-360x640` / `tablet-768x1024` / `landscape-844x390` 三行**英语**红了 9 条：
最后一行卡片的价格和倒计时压在底部那颗「+ 上架物品」按钮上。

拍卖网格**没有 mask，只有画不画的 cull**，条件是 `y + AUC_CELL_H >= listY && y <= listY + availH`
——「**顶边在视口里就整张画**」。也就是说底部那一行本来就会往视口外画最多一整个卡片高，只是
**行边界正好落在哪儿**决定了它咬不咬人；把格子高抬 20 px 就够把它推过去了。顶边那个条件同理：
往上滚到一半的那行会整张画出来，盖住上面的分类条。

改成和打造/背包网格同一个形状（`gridLayer` + `clip` Graphics + 换 `core.bodyLayer`）。原来那条
「不设 mask，所以一行要么整张画要么不画」的注释**从来就不成立**，已经改掉。

**这条的教训**：一个看起来只是「+20 px」的常量改动，会把**依赖巧合的几何**暴露出来。别把红当成
「新改动写错了」——先问「它是不是本来就错，只是以前没被踩到」。这次是后者，而且修法比回退好。

**这一节最该记住的一条**：`npm run test:portrait` 全绿只是「没有超过阈值的重叠」，不是「这一屏是对的」。
这一轮有三条真缺陷（战役地图标题、拍卖倒计时、主城队列表头）在报告上都是 0，全部来自逐张读 PNG。
§50.9 的那句「逐张读图」不是流程洁癖，是这套门禁的**必要补集**。

## 52. 签到月历竖屏：格子被宽度钉死、富余喂了行距；顺带补上「图标从来没被门禁量过」这个洞（2026-09-14）

### 52.1 先把归因摆正：不是朝向问题，是视口问题

把两张截图的尺寸代进 `ScalingManager` / `PortraitLayout` / `LandscapeLayout` 算一遍，结论跟直觉相反——
**两边的格子在设计空间里几乎一样大**，差的全在设计 px → 屏幕 px 那一步：

| 视口 | 设计矩形 | 缩放 | 格子（设计 px） | 日期数字 | 奖励「+N」 | 奖励图标 | 里程碑角标 |
|---|---|---|---|---|---|---|---|
| 报告里的横屏窗口 1861×855 | 2351×1080 | **0.792** | 280×129 | 33.2 | 25.3 | 26.1 | 15.8 |
| 报告里的竖屏窗口 422×615 | 1080×1920 | **0.320** | 165×132 | **13.5** | **10.3** | **10.9** | **6.4** |
| iPhone 13 竖 390×844 | 1080×2337 | 0.361 | 165×132 | 15.2 | 11.6 | 12.3 | 7.2 |
| **手机横屏 844×390** | 2337×1080 | 0.361 | 278×129 | **15.2** | **11.6** | **11.9** | **7.2** |
| 桌面横屏 1366×768 | 1921×1080 | 0.711 | 223×129 | 29.9 | 22.8 | 23.5 | 14.2 |

（后四列是 CSS px。）最后两行是这张表的重点：**手机横屏和竖屏一样糊**，桌面横屏才是好看的那个。
「横屏没问题」只是因为报告者的横屏窗口是 1861 宽的桌面窗口（0.792×），竖屏窗口是个 422 宽的小窗（0.320×）。
真机上横竖一样。根因就是 §49.1 记过、至今没做的那件事：竖屏设计宽度钉死 1080。

**§49.1 的可读性下限在这一页一点忙都帮不上**，这点值得单独说，因为它解释了「为什么巡检全绿而页面不能看」：

- 下限抬的是**低于 `fontFloorDesignPx(scale)`（手机上 20 设计 px）的字号**。签到格里的字号是
  `snapFont(ch × 0.32 / 0.24 / 0.16)` = **42 / 32 / 20**，全在下限之上，**一个都没被抬**。
  下限管的是「某个 token 选小了」，这里是「整套尺度对这个视口太小」——不是一回事。
- 唯一压在下限上的是里程碑金币角标（20），而下限自己**封顶在 `bodyLg`**，于是它落在 6.4–7.2 CSS px，
  低于下限自己承诺的 7。这正是 §49.1 结尾「没买到什么」那段说的东西，在这一页原样复现。
- **下限只管文字，完全不管图标。** 奖励图标 `ch×0.26`、角标金币 `ch×0.16`、绿勾 `ch×0.42` 都是直接按
  格高算的 sprite，没有任何下限。截图里真正认不出来的就是这两个 glyph——它们还是手绘笔触，
  笔画宽度跟着一起缩，10 CSS px 上就是一团墨点。

### 52.2 本页真正能改的那一刀：富余高度喂错了地方

竖屏的 `cellH = Math.min(areaH * 0.78 / ROWS, cellW * 0.8)` 里**赢的一直是右边那项**（143 vs 184），
也就是格子被**宽度**钉死；§10.10 加的 `spread` 逻辑把剩下的高度**全摊成了行距**——
390×844 上每行 159 设计 px 的间距对 143 的格子，**网格纵向 48% 是空白**。

但格内一切都是 `ch` 的比例（数字 0.32、奖励 0.26/0.24、角标 0.16、绿勾 0.42），
**格高是唯一能够到它们的旋钮**，所以这部分花在行距上等于白扔。

改法（`client/src/scenes/DailyScene/panels/checkin.ts`）：**先算高度、纵横比只当封顶**——
`gridTop` / `gridAvailH` 提到 `cellH` 之前算，竖屏 `cellH = min((gridAvailH − rowGap×(ROWS−1)) / ROWS, cellW × PORTRAIT_MAX_ASPECT)`，
剩下的才摊成行距。横屏分支（`min(areaH×0.78/ROWS, cellW×0.8)` + 固定 `h×0.006`）**逐字节不动**。

`PORTRAIT_MAX_ASPECT = 1.25` 不是拍脑袋：字号梯子的顶是 `FS.display`（60 设计 px），
而日期数字是 `ch×0.32`，所以 `ch` 过了 ~190 数字就不再长、旁边的「+N」却还在长，
`snapFont` 会把两者都吸到 60 上——**格内层级当场倒过来**。1.25 让 `ch` 落在 206，正好卡在那之下。

效果（390×844，CSS px）：格子 132 → **206 设计 px（+56%）**，行距占比 48% → 19%：

| | 日期数字 | 「+N」 | 奖励图标 | 里程碑角标 |
|---|---|---|---|---|
| 旧 | 15.2 | 11.6 | 12.3 | 7.2 |
| 新 | **21.7** | **15.2** | **19.1** | **11.6** |

**横屏没跟着改**，虽然它也有约 16% 的富余：横屏格子涨 16% 之后日期数字仍然吸附在 42 这一档（不动），
只有图标能从 11.9 涨到 14.1——收益小，而代价是动一个报告者明确说「看着没什么」的版面。记在 52.5 的清单里。

### 52.3 taller cell 立刻撞出来的东西，以及抓到它的是新门禁

新格子一上去，**里程碑格的两位数日期直接压在自己的 `+40` 上**（14/21/30 三格，重叠 33%）。
成因干净利落：角标钉在格子**右上角**、按 `ch` 算大小；数字**居中**、也按 `ch` 算大小；
**决定它们会不会碰的那个维度——格宽——在两边的公式里都不出现**。
横屏格子 2.2:1，宽度富余，永远碰不上；竖屏新格子 0.8:1，当场就碰。

改法：竖屏给角标**留出顶部一条**（`NUM_TOP_FRAC = { landscape: 0.06, portrait: 0.22 }`）。
**30 格一律留**，不只给带角标的那 4 格——30 个数字在同一条基线上，才还读得出是个网格；
taller cell 正好付得起这条（数字底边 ~0.61 ch，奖励图标顶边 0.66 ch）。

这条重叠是**真浏览器巡检报出来的，不是肉眼看出来的**——我自己看 390×844 的 PNG 时没注意到。
值得记一笔：几何改动的第一轮回归，往往就在你刚改的那几行的正下方。

### 52.4 门禁：`iconTag` + `layoutAudit` 的 `icon` 一类

图标之前**从来没被量过**：art 解码之后一个 icon 就是普通 `Sprite` 装在普通 `Container` 里，
走显示树时跟任何别的图片没有区别，所以 §49.1 那套下限只够到文字。

- `client/src/render/iconTag.ts`（新）——`tagIcon(node, id, size)` 往 `name` 上盖 `icon:` 前缀、
  往节点上盖 `iconPx`，跟 `fastText.ts` 的 `tagged()`（`txt:` / `fsPx`）是同一套路子、同一个理由。
  盖的是**调用方要的尺寸**而不是 bounds：art 是 contain-fit 进方框的，非正方的图 bounds 比框矮。
- 三个叶子构造器全部盖章：`buildRasterTabIcon` / `buildInkIcon` / `buildMaterialIcon`；
  `buildIcon` 再用 **kind 覆盖 url**（见下面第二个坑）。
- `layoutAudit.ts` 加 `icon` 一类：有效尺寸 = `iconPx × 局部缩放`，门槛 `minIconDesignPx`
  **就等于文字那条下限**，`auditOptionsFor` 里同源。

**门槛为什么不敢定高**：要抓到本页 34 设计 px 的奖励图标，门槛得是文字下限的 1.7 倍，
那会把全游戏大部分图标一起报出来——因为它们小的原因都是同一个（52.1 的 0.36×）。
**永远红的门禁不是门禁。** 所以这条只抓那件本来一个人都没在看的窄事：
**图标画得比它旁边的字还小**。老实说：**它抓不到这次报告的那个 bug**，它抓到的是别的。

两个必须点名的坑，都是自己踩出来的：

1. **`buildMaterialIcon` 不能盖在 sprite 本体上。** `sprite.width = size` 的实现是
   `scale = size / texture.width`，这个图集是 128px 帧、画 20px，于是世界缩放 = **0.16**——
   而门禁正是读世界缩放来分辨「有人把它缩了」和「它本来就这么大」。盖在 sprite 上，
   全游戏的材料 chip 都会被报成「被缩到 1/6」（光 `equipment+craft` 一站 23 条假 finding）。
   改成跟另外两个构造器一样**盖在 wrapper 上**，wrapper 自己的 scale 是 1，数才是门禁以为的那个数。
2. **finding 的名字是 webpack 内容哈希。** 两个叶子构造器只看得见 art 路径，而
   `assetModuleFilename: 'static/[contenthash][ext]'` 在 dev 也生效，于是报出来是
   `tiny icon "8ee6d0c38b3ae9553c2a"` ——什么都没说。`buildIcon` 手里有 kind，就在那里覆盖。

**门禁真报出来的三处（都是原有问题，本轮一并修了）**：`lock` 18 设计 px（equipment / cardRoster，
6.5 CSS px）、`achievements` 的金币 19、`stats` 的播放 19。前者是写死的字面量 18 —— 而 18 正好是
`FS.body` 的基准值，改成读 `FS.body` 之后**桌面一个像素不动**、手机被下限抬到 20，并且跟它旁边
一直就是 `FS.body` 的「×N」角标对齐了。后两者是 `rowH * k` 这种比例尺寸，新增
`fontScale.ts#iconFloorPx(px)` —— **`snapFont` 之于比例字号，就是它之于比例图标**：只抬到下限，
不吸附到字号档位（图标没有落在排版档位上的道理）。抬的那个下限跟门禁用的是同一个
`fontFloorDesignPx`，两边同源。

**豁免一类：重复的 pip（`untagIcon`）。** 门禁的前提是「图形没有退路」——字糊了还是个已知长度、
已知位置的词形，图糊了就只剩一团墨。等级星**正好相反**：意义在**一排有几颗**，
三个金点照样读成三。按文字下限卡每一颗，一个手机视口报 **231 条**。
所以 `render/levelStars.ts` 的每颗星 `untagIcon`。**这是对门禁的豁免、不是对问题的豁免**：
12–15 设计 px 的星在手机上确实只有 ~5 CSS px，而且**光调大常数没用**——
每个调用方都传了 `maxW`，行变宽就被原样缩回去，它要的是宽度不是常数。一并记进 52.5。

### 52.5 验证 / 没做的

- **看过**：本机真 Chrome（500×615，`designScale` 0.320，跟报告截图同一个缩放）改前/改后各拍一次对比；
  巡检自带的 `client/portrait-report/phone-390x844/daily.png`（dpr 2）改前/改后各读一张——
  第一张上那三处数字压角标清清楚楚，第二张干净。
- **数值核对**：横竖屏 7 个视口把新旧公式都算了一遍（格高、行距占比、四个 glyph 的 CSS px、网格是否还装得下）。
- `tsc --noEmit -p tsconfig.test.json` + `tsconfig.fulllink.json` 干净；`npm run lint` 0 error；`build:web` 过。
- 新增 `client/test/ui/dailySceneCheckinCellHeight.ui.ts`（3 例）：竖屏格高（读日期字号，旧公式是 42）、
  竖屏数字必须在角标下方且 30 格同基线、横屏 y/字号/数字与角标的相对位置跨绝对尺寸逐字节不变。
  **断言里没有一个量文字宽度**——headless 适配器的 `measureText` 是 `length × 7` 且无视字号，
  宽度类的重叠断言在那里测的是 harness 不是版面；真宽度归真浏览器巡检管。
  既有 `dailySceneCheckinRowSpread.ui.ts`(5) / `dailySceneCheckinFocus.ui.ts`(12) 无回归。
- **门禁复跑**：`npm run test:portrait --grep "(phone-390x844|landscape-844x390)$"`。改前那一轮是它报出了上面 52.3 那三处重叠 + 231 条 pip + 23 条 material 假 finding；收尾那一轮两个视口 36 站全绿。过程中碰到两次跟本轮无关的工具拖抽（`Execution context was destroyed` / `__nwE2E.app is missing`），单独重跑即绿。

**没做的（按值得做的顺序）**：

1. **竖屏设计宽度**（§49.1 那件大事）。本节所有数字的分母都是它。没动。
2. **等级星在手机上 ~5 CSS px**。`buildLevelStars` 的 12–15 设计 px + 调用方的 `maxW` 收缩，
   三个场景（equipment / cardRoster / auction）要连带重排才动得了。已从门禁豁免，问题仍在。
3. **横屏格子还有 ~16% 富余**（52.2 末尾）：字号梯子吃掉大半收益，暂不动。
4. **`tiny` 这一类没有加 CSS px 判据**。想过，做不了：下限自己封顶在 `bodyLg`，
   360 宽机器上本来就够不到 7 CSS px，加了这条门禁在那一行**永久红**。等第 1 项。

## 53. 状态标签：文字换图标，按量出来的宽度而不是朝向（2026-09-15）

**起因**：用户截了一张竖屏「每日任务」的图，圈出每张卡右边的「In progress」，提议 **横屏宽、文字带描述；竖屏窄、只留图标**。

方向对，但两处要改：

### 53.1 判据不是朝向，是量出来的宽度

「位置窄」有三个成因，朝向只是最吵的那个：竖屏、德语（逐词最长）、中文（全宽且无断点）。
`if (this.landscape)` 只挡第一个。这条教训仓库里已经写过两遍——
`DailyScene/panels/index.ts` 领奖按钮的注释（「按实测文字宽度算，对朝向和语言都成立」）、
`BattlePassScene/cell.ts` 的 `Gesperrt` 在 465 宽格子里吃掉 282 px（§50.12，**横屏也会犯**）。

于是新增 [`ui/widgets/statusTag.ts`](../../client/src/ui/widgets/statusTag.ts)，和 `buttonLabel.ts` 互为镜像：

| | 是什么 | 挤不下时丢什么 |
|---|---|---|
| `drawButtonLabel` | 对「点下去会怎样」的承诺，**词是载荷** | 丢**图标**，词保持原字号（`minFit`） |
| `drawStatusTag` | 行本身已经用底色/边框/位置半说出来的**事实** | 丢**词**，留字形 |

两者都**不缩到可读下限以下**；`drawStatusTag` 干脆完全不缩：字形按 `ICON_RATIO × fontSize` 画，
比它替换掉的那行字更大，所以**只要原来的词过得了巡检的 `tiny` 门禁，降级后的字形就过得了 `icon` 门禁**
（`testing/layoutAudit.ts`：「读不清的字还是个词形，读不清的图标只是一团墨」）。
返回值是实占宽度，调用方拿它算自己那一侧还剩多少（每日任务卡的折行宽、战令格的奖励带）。

**只给有公认字形的状态用**：done/claimed = `check`，locked = `lock`。
拍卖行那七态（Sold / Cancelled / Expired / Leading / Outbid / Won / Lost）**不换**——没有一套约定俗成的图标，换了是猜谜。

### 53.2 每日任务这条，比「换图标」还该更狠：那行字是零信息

三个日常任务是二值的（`shared/src/retention.ts` `DAILY_TASKS`，各 1 点、做一次就完），
所以「In progress」=「还没做」=「卡片没变绿」。换成沙漏只是用更少像素说同一句废话。

**改法**：完成 → `✓ Done`（`drawStatusTag`）；未完成 → **什么都不画**。
连带把 label 的 `wordWrapWidth` 从写死的 `cardW * 0.6` 改成「卡宽减去标签实占」——
那条 60% 上限当初就是为了躲开右边的状态字，现在未完成的卡上已经没有东西要躲。
`daily.tasks.pending` 三语一并删掉（`i18n-no-dead-keys.test.ts` 会盯）。

### 53.3 重复的格子 ≠ 一次性的行：战令走纯字形

一轮改完先截了图，战令那一屏**更吵了**：Lv.1 时 40 格里 39 格 locked，
于是屏幕上印了 39 遍 `[锁] Locked`——比原来光一个词的版本墨还多，而且没多说任何事。

所以分成两种情形，判据是**这个格子重复几遍**：

- **一次性的行**（成就档位、充值里程碑、邮件领取横幅）→ `drawStatusTag`，有地方就带词。词只出现一次，值那个宽度。
- **重复的格子**（战令 40 格）→ **纯字形**，直接 `buildIcon`，不经过这个 widget。
  顺带把 §50.12 给那格打的两次德语补丁彻底解决：`Gesperrt` 占 282 px，一把锁占一个字形宽，
  奖励带拿回去的宽度立刻看得见（`×60` 不再被挤）。

`pass_required` 本来就是纯字形，这轮只是把三种字形的尺寸统一成同一个 `tagH`，
省得一列格子在两种锁尺寸之间跳。`battlepass.claimed` / `battlepass.locked` 三语删掉——
再也不画了，留着就是 dead copy。

### 53.4 顺手修的：成就领取按钮在横屏手机上被切两头

`achievement.claim`（"Claim +200"）的按钮宽是写死的 `rowH * 1.9`。
横屏手机（844×390）行矮 → `bh` 小 → 字号小（**设计 px**），但整屏在 0.36x 上渲染，
`drawButtonLabel` 撞到可读下限就停止缩小、任由文字溢出（它自己的 §50.12 规则）——于是金色框两头都被切掉。
改成按实测 label 宽定宽、`rowH * 1.9` 只当下限，跟 DailyScene 领奖按钮同一个修法。

**这个缺陷巡检从来没报过，因为巡检的号从来没有过一个可领的档位**——见下条。

### 53.5 巡检漏的洞：一个场景只走默认那个 tab

用户那张图之所以能活到被截图，是因为**竖屏巡检根本没走到那个 tab**。
`layoutStops.ts` 的 `daily` 站只进场，落在哪个 tab 由 `DailyScene.pickInitialTab` 从存档推（新号 → 签到页）。
Daily 另外三个 tab、拍卖行的 `mine`/`bids` 两个 tab 全没审过。

补了四站（用 `Hop` 的 `tap` 形式，点 tab 自己的标题，跟玩家一样）：
`daily+tasks`、`daily+weekly`、`auction+mine`、`auction+bids`。

**同时给 seed 补状态**，否则新站只能审到空壳：

- `save.retention.daily/weekly` 摆成**半完成**（三任务完成一个、三档周奖励领掉一档且下一档已达成）——
  带状态标签的恰恰是 done/claimed 那一半形态，全新号一个都渲染不到。
- `save.achievements` 给 `ach.campaign.chapters` 领掉档位 I（号本来就通关了第一章，档位是真达成的）。
- `auctionBids` 集合（My Bids 读的是这张参与流水，不是 `topBid`）——不喂它，那个 tab 在 44 条挂单的市场上渲染空状态。

### 53.6 怎么核的

没有后端。`TARGET=web-e2e` 的 `__nwE2E.views.showXxx(stub)` **直接挂场景**，
桩里塞进想看的状态，一个服务都不用起（同 `worktree-session-cannot-start-dev-server` 那条记忆）。
三个视口 × 六屏：`390×844`、`844×390`、`360×640` 德语。

**一条诚实的观察**：这六屏在三语三尺寸下，`[字形][词]` 这一对**都塞得下**——降级分支一次都没触发。
也就是说本轮真正改观的是 53.2（删掉零信息的词）和 53.3（重复格子只留字形），
而 53.1 那套降级是**给还没发生的字符串和盒子留的保险**。
保险没人走过就等于没有，所以补了 `test/ui/statusTag.ui.ts` 把三条契约钉住：
塞得下 → 字形+词；塞不下 → 丢词不丢字形；盒子比字形还窄 → 照画不缩（那是巡检该报的版面 bug，不是该悄悄糊掉的东西）。
