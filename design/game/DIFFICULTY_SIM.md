# 关卡难度模拟器（PvE Balance Tool）

> 用真实确定性战斗引擎 + 一个基线玩家 AI，量化战役关卡难度。
> 代码：`client/test/difficultySim.ts`（核心）/ `test/difficulty/`（难度矩阵+回归守卫，
> `core.test.ts` 确定性+单调性 / `chapterReport.ts` 共享 + `ch1..ch6.test.ts` 每章一个文件）/
> `experiment.test.ts`（关卡调参 A/B）/ `diag.test.ts`（单关逐秒时间线检视）。
>
> **PvP 平衡用另一支模拟器**（本工具不适用 PvP——单防守 AI 无进攻 macro，镜像必平局）：
> `client/test/pvpSim.ts`（+ `pvpSim.test.ts`）复用 siege 确定性双军引擎作等墨对撞台，
> 量度残存军队血量定标单位费用。背景与 P4 结论见 `PVP_LOADOUT_DESIGN.md §5` + `BALANCE.md §5.2`。

## 这是什么

战役关卡此前**没有**任何难度评估手段，全靠手感。本工具用 `@nw/engine`（30Hz、
确定性）无渲染地跑一整场战役，由一个固定策略的「基线玩家 AI」自动防守，输出：

- 能否通关（survive：撑到波次耗尽且清场）
- 结束/最低基地血、撑了多少秒、首次破防时刻
- 峰值同屏敌人数 / 总血量

并提供上层能力：
- **评星** `SimResult.stars`：**复合评分轴**（2026-07-11 起，见 `STAR_SCORING.md`）——
  由 hp / speed / leak 三个子分按关型加权成综合分 `S∈[0,1]`，对照 `level.rewards.starThresholds`
  （已统一为综合分×100 门槛 `[1,50,80]`，**不再是 HP% 门槛**）。`computeStars(thresholds, ctx)`
  与游戏 / 裁判同一函数；`difficultySim` 用 `buildStarContext` 从 `engine.state.snapshotSummary()`
  + `snapshotStats()` 组装 ctx（与 `judgeRunner` 逐字段一致）。胜利保底 1★，基地被打爆 0★。
- **多种子评估** `evalCell(levelId, preset)`：用 `EVAL_SEEDS`（5 个固定种子）各跑一局，
  取**通关率**与**中位星级**——换 seed 即换发牌/抽卡顺序，抹平单局噪声，星级才可信。
- **养成门槛扫描** `findClearThreshold(levelId)`：fresh→T2…T6 逐档多种子跑，找通关率≥50% 的最低养成。
- **关卡调参 A/B** `simulateLevel(levelObj, …)`：传入改过参数的关卡对象（startInk /
  inkRegenMult / enemyScale / 波次 atTick·count），对比下调方案效果。

### 跑法

```bash
cd client
npx vitest run test/difficulty        # 难度矩阵（全部 6 章 61 关 × 养成预设）+ 确定性/单调性守卫
npx vitest run test/difficulty/ch3    # 只跑第 3 章（10 关），迭代单章调参时更快
npx vitest run experiment              # ch1_lv1 各下调方案对比
npx vitest run diag                    # 单关逐秒时间线（改 diag.test.ts 顶部 LEVEL_ID/PRESET 可指向任意关卡）
```

**CI 提速（2026-07-16）**：`difficulty.test.ts` 原来把 61 关 × 6 档 × 5 种子的 report
用例塞进一个 `it()`，单线程跑要 ~150s，是 `npm test` 步骤的绝对瓶颈（也是 CI 一次跑
近 6 分钟的主因）。现在拆成 `test/difficulty/`：`core.test.ts`（确定性+单调性，几毫秒）
+ 每章一个文件（`chapterReport.ts` 共享 `describeChapterDifficulty()`，`ch1..ch6.test.ts`
各自只跑自己章节的 10 关）。vitest 按文件分发到独立 worker 线程，6 章从串行 150s
变成并发跑，本机（22 核）全量 `npx vitest run` 从 152s 降到 ~60s；CI runner 核数更少，
增益会小一些，但仍显著优于单文件串行。**若要新增关卡/章节，别把 report 用例塞回
一个大 `it()`——按章节（或更细）拆文件才能吃到 vitest 的文件级并行。**

## 复合评分轴切换 + ch6 收尾修复（✅ 已应用 2026-07-11）

**动机**：旧评分只看基地剩余 HP%，塔防里「守住 = 不漏 = 满血」→ 一旦通关就是 3★，星级
二极化、无梯度（玩家反馈「通关即三星、三星之间没差别」）。切换到**复合评分轴**
（`STAR_SCORING.md`）：hp/speed/leak/kill 四子分按关型加权，进攻类关卡即便守得完美也按通关
速度分档。全 61 关 `starThresholds` 统一重设为综合分门槛 `[1,50,80]`（ch0 教程 `[1,1,1]`）。

**timed_defense 的第二根轴**：这类关时长固定 → speed 无意义、HP 类指标全塌成终局残血，偏易时
仍二极化。补上 `killScore`（歼灭率 = `unitsKilled / 计时内应刷敌人数`），timed_defense 用
hp + kill 各半——「守稳且清场压制」才 3★。效果：`ch1_lv6` 从「全档平 3★」变成 2★→…→T6 3★，
`ch1_lv9`/`ch3_lv7`/`ch6_lv2` 等也出现阶梯。`unitsKilled` 已在 `PlayerStats`，无需额外 plumbing。

**关键结论：只换评分轴、不动任何难度数值，星级立刻散开**——`ch1_lv3` 出现 1★→1★→2★→2★→3★→3★
的干净阶梯，`ch1_lv1` fresh 2★ / T5 才 3★。同时体感变难（fresh 通不过半个 ch1、3★ 要速攻+
无伤），「又偏简单」一并缓解。基线 AI 保守、清场慢 → 常卡在 2★，人类速攻可上 3★，是健康余白。

**唯一退行 + 修复**：`ch6_lv9`(leak_limit)/`ch6_lv10`(boss) 变 `unbeatable`——与评分轴无关
（胜负不看星），是 07-05 之后 PvP 经济调整（墨上限 300→100 等 `config.ts`）削了基线 AI 经济
的副作用。这两关（最终章、hazard 密集）单独放宽经济：`ch6_lv9` maxLeaks 1→2 / startInk 26→40 /
regen 1.36→1.65 / enemyScale 1.24·1.18→1.14·1.10；`ch6_lv10` startInk 32→46 / regen 1.46→1.75 /
enemyScale 1.2·1.14→1.12·1.08。复核后 `ch6_lv9` T6 80%(3★)、`ch6_lv10` T5/T6 60%(1★)，
**全 61 关恢复「均有可清档位」**。

## 基线 AI 策略（启发式 v2，非最优）

每 tick 用令牌桶按 `actionsPerSecond`（默认 8，模拟熟练玩家 APM）连续出手，优先级：

1. **流星 AOE**：某车道聚 ≥2 敌人就砸（每 tick 一发）。
2. **防线覆盖 + 标准 TD 阵型**（最高战术优先）：任何来敌车道阻挡 < `blockersPerLane`（默认 2）
   就在最逼近的欠守道补兵——**该道还没坦克 → 先盾兵扛线；否则优先弓手（清场主力 DPS），再退步兵**。
   本游戏防御主力是野战单位，必须每条来敌道都有「坦克扛+输出跟」。
3. **箭塔骨架**：覆盖满足后补塔（塔在 row0、射程 2，是后排火力，非主力）。
4. 兵营（被动出兵流）。
5. 余力继续按阵型分摊到防守最薄弱的来敌道。
6. 经济：场面安全且有余钱就升基地（默认追到 3 级，提升回墨）。

v2 相对 v1 的关键修法（v1 几乎全 ch1 不过）：令牌桶按真实 APM 花墨（别节流卡死）+
**每条来敌道都要有兵、分摊防守（别全堆一条道漏光其它道）** + **坦克扛+弓手输出阵型**（能清场而非只僵持）。

### ⚠️ 重要局限（解读结果必读）

基线 AI v2 已能扛大场面（给足经济可守 lv9 的 111 同屏敌、稳过 lv1/lv2），但**仍弱于熟练玩家**。
因此：

- 评星对**调好的关**可信（如 lv2 出现干净阶梯：T4=1★→T5=3★）；对 AI 过不了的关只说明「偏难/过载」，不代表人类也过不了。
- **绝对通关与否偏保守**：AI 轻松过 ⇒ 偏易；AI 勉强过/过不了 ⇒ 偏难。
- 调参 A/B 看的是**方向**与量级，不是精确数值。
- **法术盲区**：AI 只用流星（单点 AOE）。Haste（buff）和关卡专属法术 Rockslide/Bridge Collapse
  （地形/控场类）targeting 语义特殊，AI 完全不会用——含这些卡的关卡，AI 的评估会比实际更悲观。

## 兵种角色泛化（2026-07-05：从 ch1-only 扩到全部章节）

AI 最初硬编码只认 ch1 三兵种（infantry/shieldbearer/archer）。ch2 起的关卡 loadout 会给
Max/Lena/Mara（甚至 PvE 专属单位），AI 不认识就完全不用——相当于「拿到好牌不知道怎么打」，
之前从未跑过 ch2+ 就是这个原因。

现在改成从 `UNIT_BLUEPRINTS` 的静态 hp/attack/range 派生角色（`ROLE_MAP`），不再硬编码兵种名：

- `attack === 0` → support（如 Medic，纯辅助，最后才选）
- `range ≥ 2` → ranged（Archer/Mara，主输出）
- `hp ≥ 140` → tank（ShieldBearer/Ironclad/Lena/Max，扛线）
- 其余 → melee（Infantry/Runner/Berserker/Splitter/Harpy，平衡位）

`reinforceLane()` 补线优先级从「缺盾兵→先补盾兵，否则弓手，否则步兵」泛化为
「缺 tank 角色→先补 tank，否则 ranged，否则 melee，否则 support」，对任意关卡的实际
loadout 都能摆出「坦克扛+输出跟」的标准 TD 阵型。

## 装备预设

`progressionCards(preset)` 现在除了给 6 个可养成兵种（`PROGRESSABLE_UNITS`：
Infantry/ShieldBearer/Archer/Max/Lena/Mara）按档位升级，还会挂一套「档位对应装备」
（`PROGRESSION_GEAR` + `PROGRESSION_EQUIP_INV`，`difficultySim.ts`）：

| 档位 | 装备 |
|---|---|
| fresh | 无 |
| T2/T3 | 武器（主词条 m_atk +8%，强化 0 级） |
| T4/T5 | 武器 + 护甲（m_atk +8% / m_hp +10%，强化 3 级） |
| T6 | 武器 + 护甲 + 饰品（m_atk / m_hp+s_armor / m_crit，强化 6 级） |

⚠️ **这套数值是模拟器占位值，不是游戏权威数值**——装备强化系数用的是
`server/engine/src/balance/equipment.ts` 里真实的 `AFFIX_FIELD_MAP`/`ENHANCE_LEVEL_MULTIPLIER`
机制（[ADR-063](DECISIONS.md) 起改为非线性倍率表），但具体数值（+8 atk、+10 hp…）是为了让「档位=卡等级+合理装备」这个模型跑起来而取的
估计值；`ECONOMY_NUMBERS §5` 的装备数值权威表还未定稿，以后定了要回来对齐这里。

**影响**：接入装备后同档位比纯卡等级更强，ch1 矩阵数值会整体比装备接入前的历史记录更容易
（例如 lv4/lv7/lv8 min通关从 T4 降到 T2）——这是装备叠加的预期结果，不代表关卡本身变简单了。

## 护送目标（escort objective）

胜负判定本身不需要改引擎——`GameEngine.checkWinCondition()` 对 escort/leak_limit/
destroy_base 等目标类型已经原生支持（到达即赢/全灭即输，`state.escorts[].status`
自动流转），`simulateLevel()` 原有的 `win = engine.state.winner === Side.Bottom`
判断直接适用。`destroy_base` 也不需要额外的「进攻 AI」——本作防守单位清线后本来就会
自动前进破坏敌方基地（`MovementSystem`），基线 AI 现有的补线逻辑天然兼容。

真正缺的是 AI 的护送防守意识：加了一步「护送预判防守」——只要还有 escort 处于
`moving` 状态，AI 会主动把它当前所在列补到 `blockersPerLane`，**不等敌人真的逼近才
反应**（`pickUnescortedLane`，优先级在流星之后、常规补线之前）。`SimResult` 新增
`escortMinHp`（护送单位全程最低血量，无护送关为 null）和 `enemyLeaks`
（leak_limit 诊断用）两个字段。

## ch2_lv3 护送关诊断 + ch2–ch6 系统性重调（✅ 已应用 2026-07-05）

### 根因诊断：不是逐秒磨血，是「深入敌境时无人可用」

用 `diag.test.ts` 改造的逐 tick 追踪（T6/seed 65537）逼近 `ch2_lv3` 护送单位死亡
瞬间，发现两个关键事实：

1. **基地侵蚀和护送死亡是两件不相关的事**：基地在 t≈24–28s 被一波（tick 780）打到
   34% 血后就再没掉过；护送单位在此期间毫发无损（260/260），直到 t≈40s 才开始掉血，
   8 秒内被打空——**是一次集中爆发，不是全程缓慢放血**。
2. **ink 全程个位数**：整场 ink 从未超过 16，且这个量级贯穿始终——因为
   `ch2_lv3.json`（以及全部 ch2–ch6 关卡，除 `ch2_lv2/lv7` 外）**从未设置 `startInk`/
   `inkRegenMult`，等于默认 0 起手 + 1x 回墨**，跟 ch1 重调前一模一样。护送单位在
   t=40s 走到 row12–14（靠近敌方本阵）时，AI 早被 t=26s 那波base急救掏空了 ink，
   没有余力再在护送深入敌境的位置补防——**输的不是血量或速度，是经济破产后没有防守
   资源可用**。加血/加速本身（试过 speed 0.25→0.5、hp 260→400、enemyScale 砍到
   1.0/0.9，单独或组合）对 `escortMinHp` 完全无效——因为死因不是数值不够，是「没人
   防守」。

**结论**：`ch2_lv3` 和 ch3–ch6 大面积 `unbeatable` 是**同一个根因**——这些关卡从
authored 起就没做过 `tune-ch1.cjs` 那样的经济重调，只是把敌人数量线性堆到 ch1 的
2–3 倍（40→144），经济旋钮原地不动。这不是设计上「后期关卡该更难」的意图体现，
是数值从未被回访。

### 重调：`tune-ch2-6.cjs`，把 ch1 的经济 on-ramp 套用到全章节

沿用 `tune-ch1.cjs` 的相对变换手法（不改 objective/loadout/rewards/seed/波次结构，
只调经济与强度旋钮），脚本 `client/scripts/tune-ch2-6.cjs`：

- **`startInk` + `inkRegenMult`**：按 `((chapter-2)*10+(level-1))/49` 的连续进度 p
  （ch2_lv1→0，ch6_lv10→1）插值，`survive`/`destroy_base`/`escort`（对 AI 更难）给更
  多经济、`timed_defense`/`boss`/`leak_limit`（本就容易稳住）给略少经济，呼应
  `tune-ch1.cjs` 的差异化思路。
- **`enemyScale`**：hp 1.0→1.15、dmg 1.0→1.08~1.12 随 p 缓升，远低于原始波次数量的
  涨幅——伤害曲线交给「更多经济防更多敌人」而不是「敌人更肉更疼」。
- **首波 `atTick`**：统一顶到 120（4s），给布防窗口（原来几乎全是 60=2s，`ch2_lv2/
  lv7` 等已有更晚首波的关卡不倒退）。
- **敌人总量**：从原始 authored 值（40→144，近 4 倍膨胀）压到 `28 + p×48`（28→76），
  远低于原值但仍高于 ch1 的 ~50 上限，保留章节间的强度递进感。
- **护送关**（`ch2_lv3`/`ch3_lv4`/`ch5_lv5`）额外把 `escorts[].hp` ×1.25——经济修复
  让 AI 能在护送单位深入敌境时补防，血量 buffer 再给一点容错。

+lava）、`ch6_lv10`（boss，最终关，fog/lava/speed 多 hazard 叠加）三关仍在 T6 卡在
40% 以下——这三关本身就是章节里 hazard 密度最高的设计，给它们单独加码经济

整体递进（ch1 最易 → ch6 收尾最难）。

**方法**：5 个 agent 各领一章并行工作，每章独立诊断+迭代（用 `findClearThreshold` 只
评自己章节的 10 关，不跑 61 关全量矩阵，快很多），新增 `tune-chN-precision.cjs`（N=2..6，
每关手调 POLICY 表，非公式横扫，在 `tune-ch2-6.cjs` 的经济修复基线上运行）。旋钮集合
与 ch1 精修一致，同样克制：`startInk`/`inkRegenMult`/`enemyScale.{hp,damage}`/首波
`atTick`（统一推到 4s）/波次 `count`（按目标总量等比缩放）/护送关加血，不碰
objective/loadout/rewards/波次结构本身。

**目标曲线**（章间递进，章内尽量单调，允许 timed_defense/boss/leak_limit 等 AI 天然
更易的关型有 ±1 档偏移，同 ch1 的 lv5/lv6/lv7=T4/T4/T3 先例）：

```

ch2  fresh,fresh,T2,T2,T3,T3,T4,T4,T4,T5
ch3  fresh,T2,T2,T3,T3,T4,T4,T4,T5,T5
ch4  T2,T2,T3,T3,T4,T4,T4,T5,T5,T5

ch6  T3,T3,T4,T4,T5,T5,T5,T6,T6,T6            （收尾章，最难）
```

**实际结果**（AI v2，5 种子中位，min通关；`npx vitest run difficulty` 全量复核）：

ch6 T3–T6 全场最难），章内不再是大幅无序抖动，剩下的偏差都定位到具体原因：

- **ch2_lv8**：可用卡组被砍到只剩 `max_1/max_2/meteor_1/haste_1`（无塔/兵营/Lena/
  Mara），对 enemyScale/经济极度敏感，冲 T4 必超调到 T5/T6 unbeatable，T3 是唯一稳定
  档，形成 T3→T4→T3→T4 的合理小凹陷（与 ch1_lv7 同类现象）。
- **ch3_lv7**（timed_defense）：27 波全部落在 60s 时限内且有富余，AI 撑到时限即算赢，
  总量/enemyScale 杠杆有限；改按「开局经济破产」处理（`startInk`=0、`regen`<1，比
  fresh 默认更穷）才勉强移出 fresh，未能推到目标 T4，停在 T3。
- **ch3_lv8**（leak_limit）：卡在陡峭档位边界，小幅调参会在 T3/T4/T5/unbeatable 间
  跳变，选择稳定在比目标高 1 档的 T5，好过冒险跳回 unbeatable。
- **ch5（全章最抖，也是 ch5_lv8 那个"遗留"抖动的最终诊断）**：根因是一个**引擎级
  bug**——`UnitType.Harpy`（`flying: true`，`config.ts:217-229`）只有 `ArrowTower`
  能命中（`canTargetFlying`，`config.ts:347`），而基线 AI 的 `pickUnderBlockedLane`
  会在塔到位前就先派地面兵去"堵"来袭的 harpy；地面兵进入 `Attacking` 状态后
  `MovementSystem` 不再推进它，于是永久卡在半路——打不到 harpy、也追不上，AI 还会
  持续往该道加兵，把经济拖垮到守不住其它道。`survive` 的胜利条件要求敌人清空，一只
  卡死的 harpy 就能让某些种子永远赢不了——**这才是 ch5_lv8 T3→T4/T5"反而变差"的真实
  成因：种子间方差被这个引擎行为放大，不是数值不够**。缓解（数据侧，未动引擎代码）：
  harpy/splitter 按 `capUnits` 限量到每道 1 只（而非按总量比例放大）+ 更富裕经济，让
  AI 能在多数种子下解开僵局；残余方差记录在案而非硬调数值抹平。ch5_lv3/lv5 因与 lv8
  共享同一类 AI 行为噪声，也各比目标高 1 档，属同源可接受偏差。若要根治需要修
  `pickUnderBlockedLane`（识别 flying 目标改派/改配 ArrowTower）或调整该关卡布局，
  超出本轮"只调关卡数值"的范围，留给后续。
- **ch6_lv8**（destroy_base）：两次尝试把 enemyScale 推到目标 T6 都直接冲成
  T6-still-unbeatable，退回稳定的 T5；`ch6_lv6`（survive）为脱离"即使 T6 也
  unbeatable"的地板，用了全章最极端经济（`startInk`80/`regen`2.30）+ 敌人总量下修，
  因为该关波次是大规模同 tick 敌人齐至（`count`4 同时刷），AI 的反应式补防吃不消，
  只能靠经济换喘息。

**产出脚本**（每关手调 POLICY 的单一来源，格式同 `tune-ch1.cjs`，`git checkout` 对应
`ch{2..6}_lv*.json` 后重跑即可复现，注意要在 `tune-ch2-6.cjs` 的产出基线上跑，不要
直接对未经济修复的原始 JSON 跑）：`client/scripts/tune-ch2-precision.cjs` /
`tune-ch3-precision.cjs` / `tune-ch4-precision.cjs` / `tune-ch5-precision.cjs` /
`tune-ch6-precision.cjs`。

**遗留**：仍有非单调抖动的关卡见上（ch2_lv8、ch3_lv7/lv8、ch5 全章、ch6_lv6/lv8），
均已定位到具体原因（受限卡组/AI 天然占优的关型/引擎级 flying-unit 卡死/齐至波次），
不再是未探明的噪声。ch5 的 harpy 卡死是唯一触及引擎行为而非纯数值的发现，若后续要
彻底解决需要改 AI 的 `pickUnderBlockedLane` 或该单位类型的可命中范围。

## pickUnderBlockedLane 的 flying 单位处理（✅ 已应用 2026-07-05，client/test/difficultySim.ts）

上一节记录的 ch5_lv8 根因——地面兵对 flying 敌人（Harpy）既拦不住也打不死，卡进
`Attacking` 状态后永久僵在半路——被当作模拟器 AI 的一个具体缺陷来修，而不只是留在
诊断记录里。

**第一版尝试（已回退，教训记录在案）**：让 `reinforceLane` 在车道威胁含 flying 敌人
时，只允许打出 `canTargetFlying` 的兵种卡，找不到就直接放弃出兵（`return false`），
指望后续「造箭塔」步骤去补。逻辑上更"正确"（不再徒劳送兵），但跑一次全量 61 关矩阵
后发现是**倒退**：`ch6_lv9`/`ch6_lv10` 从可通关（T6）变成 `unbeatable`，`ch3_lv3`
星级也变差。根因：目前全游戏**没有任何一个兵种**带 `canTargetFlying: true`（只有
`ArrowTower` 塔有），所以"只放能命中的兵"这个分支在实践中永远找不到牌、永远
`return false`——等于让 AI 彻底放弃在该车道出兵。而箭塔在 row0、射程 2，根本够不到
半路（诊断记录的卡死点在 row11–13）拦截，所以"造塔补位"这个后备方案对已经飞到半路
的敌人完全无效。换句话说，原来"地面兵徒劳但卡死 harpy"这个行为虽然赢不了（清不空
board），却意外提供了唯一的实际防御效果——把 harpy 钉在半路、不让它飞到基地——拿掉
它却没有等价替代，结果是纯粹变差。

**最终版**：车道威胁含 flying 敌人时，优先找 `canTargetFlying` 的兵种卡（目前是
no-op，为未来兵种预留正确行为）；找不到就照常退回原有的坦克→远程→近战→辅助编队
逻辑，**不放弃出兵**——保留这个"卡死"副作用，因为它是当前唯一在起作用的防御手段。
另外给 `pickTowerLane` 加了一条：车道威胁含 flying 敌人时优先造塔（原逻辑只按
`closestRow` 排队，flying 车道可能在预算有限时被更"紧急"的地面车道抢走塔位）。
`pickUnderBlockedLane` 的覆盖判定**刻意没有**改成只认 `canTargetFlying` 友军——同理，
现在没有任何兵种满足条件，如果这样改会让该车道永远判定为"未覆盖"，AI 会不断把兵
无限地砸进这个死局车道而不去分兵守其它道，比原样更浪费经济。

跑 `npx vitest run difficulty` 全量 61 关复核：结果与改动前的矩阵几乎逐格相同，唯一
差异是 `ch6_lv5`（该关也有 harpy 波次）T5 档由 `2★60%` 变为 `3★100%`，属改善而非倒退；
其余 60 关分毫不差。**无回归**，但也没有解决 ch5_lv8 本身的星级抖动（意料之中——已经
诊断过是受限卡组/splitter 分裂/meteor 被禁等多重问题叠加，flying 卡死只是其中一环）。

**已知局限（本节写于 2026-07-05 14:17，38 分钟后已被下条修复过期）**：该修复只让 AI
"不再往死局车道里瞎砸兵"，当时没有解决根本问题——彼时仍没有任何兵种能真正命中
flying 敌人。`types.ts:22`/`types.ts:303` 的设计注释明确写"只有箭塔和 archer
（canTargetFlying）能命中"，但 `config.ts` 里 Archer 的 blueprint 当时**从未设置**
`canTargetFlying: true`——已用 `spawn_task` 另行登记。

> **✅ 已修复（2026-07-05 14:55，`a601c6df` "弓箭手补齐 canTargetFlying"）**：Archer
> blueprint 现已带 `canTargetFlying: true`（`server/engine/src/config.ts:179`）。本节
> `pickUnderBlockedLane`/`pickTowerLane` 的判定逻辑是**动态读 `UNIT_BLUEPRINTS[unitType]
> ?.canTargetFlying`**（非硬编码"无兵种满足"），config 修复后 AI **自动**能选到 Archer

## ch1_lv1 诊断结论（关键）

引擎铁的事实（不依赖 AI 水平）：

- 敌人 **tick 60 = 2.0s** 就到，开局 0 墨、回墨恒定 **2/s**、基地升级 50/100/200——
  **没有经济起步窗口**。
  > 数值更新（2026-07-11，PvP 经济调整）：墨上限 300→**100**、基地升级 50/100/200（共3级）→**30/50（共2级）**（`config.ts`，见 `BALANCE.md §2`）。本诊断命门是「开局 0 墨 + 敌人 2s 即到」而非升级费本身，升级费下调只**略微放宽**边际、结论「无经济起步窗口」不变。
- 波次：**34 个 Max**（190 血 / 22 攻 / 残血双倍伤）+ **2 个 Lena Boss**（150 血 / 每击 -8 减伤），
  在 2s–43s 内投放，含 **tick 900（30s）一次性 12 个 Max 齐推**。敌方总血量 ≈ **6,760**。
  > 数值更新（2026-07-02，PvP 锚点平衡）：Max 攻 **22→14**（`config.ts`，见 `BALANCE.md §5.1`）。本关本诊断的命门是**开局经济 vs 敌人数量**而非单体战力（见下方结论），故敌方 Max 攻降低只**放宽**玩家生存边际、不冲击 2026-06-23 的重调；lv1 通关性未变（下方 sim 复核确认）。

调参 A/B 验证（fresh + 基线 AI）：

| 方案 | 结果 |
|---|---|
| 原版 | ✗ 34s 阵亡 |
| 只加经济（起手墨/回墨×2~2.5） | ✗（30s 的 12 连推照样压垮） |
| 只砍兵量×0.5+推迟5s（峰值仅 9 敌） | ✗（fresh 经济仍太薄，养不起防线） |
| **经济 + 节奏一起松**（起手墨30/回墨×1.3/敌HP×0.85/推迟+兵量×0.55） | ✓ **满血 100 通关** |

**结论：lv1 的命门是「开局经济 vs 早期敌人数量」，不是单体战力。**
→ **加养成（战力）救不了第一关**（fresh 撑 34s、T6 也只撑 55s，全失败）；
→ 单给经济或单砍敌人都不够，**必须经济 + 波次节奏一起松**。

## ch1 星级门槛校准 + lv5/lv8/lv10 波次方差（✅ 已应用 2026-07-26）

**动机**：玩家反馈 ch1 地图几乎全是 2★，缺乏「手牌/发挥好坏→星级差异」的区分度。原因
拆解为两条：

1. `starThresholds` 全 61 关统一 `[1,50,80]`，没有按各关实际分数分布校准，导致大多数
   「正常发挥」的 `S100` 综合分（见 `STAR_SCORING.md`）恰好落在 50–80 区间，全部收敛成 2★。
2. lv5/lv8/lv10 三关的波次节奏是平滑单调爬升，没有一个「一步错满盘皆输」的高风险时刻，
   同一档位反复挑战时表现差异很难被放大成星级/成败差异。

**方案 A：逐关校准门槛**——用 `client/test/difficultySim.ts`（`computeStarScore` 原始
0–100 分，而非取整后的星级）在 `fresh`/`T2`…`T6` 六档 × `EVAL_SEEDS` 五种子下跑出每关
实际分数分布，再按各关"目标养成档位"（即上面§ch1整章重调表的 min通关档位）附近的分数
带宽重新设定 `[1★, 2★, 3★]` 门槛，取代统一的 `[1,50,80]`：

```
lv1  [1,60,82]   lv2  [1,72,85]   lv3  [1,50,80]（分布本就理想，未动）
lv4  [1,58,78]   lv5  [1,58,80]   lv6  [1,58,78]
lv7  [1,55,82]   lv8  [1,58,75]   lv9  [1,55,85]   lv10 [1,50,65]
```

`timed_defense`（lv2/6/9）分数天花板较低（击杀率不随养成档位显著提升，因为波次总量固定），
`boss`（lv10）分数普遍偏低（约 40 分区间），因此这两类的 3★ 门槛明显低于 `survive` 关。

**方案 B：lv5/lv8/lv10 波次方差重设计**——在既有波次基础上，各选一个既有的中段簇群
（不新增波次总时长，`floorTicks`/`parTicks` 不受影响），把宽度从 2 车道拉到 6~8 车道、
间距收紧到 8~10 tick，制造一次「必须全场布防到位才能扛住」的尖峰：

- `ch1_lv5.json`：tick 600 簇群加两条外侧车道（col 0/11）+ 对称 max 齐推，间距 20→10/15→8。
- `ch1_lv8.json`：tick 780 簇群同样加外侧车道 + max 补位，col 0/11 从 count1 提到 count2。
- `ch1_lv10.json`：tick 1020（boss 战前一波）加外侧车道 max 齐推，让打 boss 前的状态方差
  被放大（血厚血薄直接决定后面能不能扛住 boss）。

**验证**（AI v3，5 种子中位，`npx vitest run test/difficulty/ch1`）：无 `unbeatable` 回归；
min通关档位 lv5→T4（与设计目标一致）、lv8→T3（原 T4 目标提前一档，胜率仍只有 60%，
非"轻松提前"）、lv10→T4（原 T3 gate 收紧、更接近 T5 目标）。逐种子星级现在在同一档位内
真实出现 `FAIL/1★/2★/3★` 混合分布，而非清一色 2★（详见运行记录，例如 lv5 在 T4 档：
`[FAIL, 2★, 1★, 3★, FAIL]`）。

**已知局限**：这套模拟仍是固定策略基线 AI，同档位 5 个种子的差异只反映"发牌顺序"造成的
分数抖动，不代表真实玩家的手牌决策空间；真实玩家的操作/组卡差异预期比模拟器展示的更大。
调参数据只用于校准门槛的**位置**，不是精确复刻真实分布。

## ch2-ch6 星级门槛校准 + 波次方差重设计（✅ 已应用 2026-07-30）

**动机**：与 ch1 同一根因，套用同一方法论（本节起 ch2-ch6 各自独立小节，方法不重复展开）。
`client/test/difficultySim.ts` 新增 `SimResult.scoreRaw`（`computeStarScore`×100 原始分，未
中签则为 `null`）：此前 ch1 校准时是靠一次性脚本临时读取，现已固化为该文件的常设诊断字段
（`computeStarScore` 本身注释即写明"Exposed for diagnostics/tuning"），后续章节调参可直接复
用，不必再重新发明一次性脚本。

**通用方法（对每章重复）**：

- **方案 A（门槛校准）**：临时 `client/test/difficulty/_scan.test.ts`（跑完即删，不进正式
  套件）在 `fresh`/`T2`…`T6` × `EVAL_SEEDS` 五种子下打印每关 `scoreRaw` 原始分布，按各关实
  际分数带宽重设 `[1★,2★,3★]`。第一项门槛恒为 `1`——`computeStars` 对任意胜利都会 floor 到
  至少 1★，故第一项数值本身不影响结果，只有第二/三项门槛真正决定星级分布。
- **方案 B（波次方差重设计）**：每章挑 2-3 关（尽量覆盖该章独有的目标类型，如 escort/
  timed_defense/destroy_base/boss，而非重复 survive），选一个既有中段波次簇群，不新增总波
  次时长（不碰 `floorTicks`/`parTicks` 的输入——最后一波簇群的 `atTick`/`count`/`spacingTicks`
  保持不变），把车道数从 2-4 拉到 6-8、间距收紧，制造一次全场压力尖峰。**幅度需要试跑校
  准**：过猛会直接把关卡跑成 `unbeatable`（ch2_lv10 第一版 8 车道/间距10 就整档 `unbeatable`，
  收窄回 6 车道/间距 18-20 才恢复原有 min_clear 档位）；`survive` 类目标的评分只看 hp+speed
  两项，加更多坦克型敌人往往只是让 AI"多磨一会儿"从而把 speedScore 拖到 0（score 收敛到
  `hp*0.5` 的一个定值），并不会自动产生分数方差——遇到这种情况方差要靠引入**失败风险**
  （某些种子直接崩线）而非期待分数本身分层。
