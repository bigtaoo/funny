## 2026-08-08：护盾/加速倒计时改天时分秒 + 护盾贴图改成持续动画（用户截图反馈）

用户截图反馈两点：①主城状态卡的 `Protected (146282s)` / `Training ×2 (86374s)` 倒计时直接显示裸秒数，玩家看不懂；②主城上叠的护盾"就是一张图"，看不出这层半透明光泡是干什么用的（§35 引入的呼吸光泡，见本文件 S8-8 条目）。

**倒计时格式**：`world.protected`/`world.speedup` 两个 i18n key 的 `{sec}s` 占位换成 `{d}天{h}时{m}分{s}秒`（en `{d}d {h}h {m}m {s}s`、de `{d}T {h}Std {m}Min {s}Sek`），复用 `AuctionScene.timeLeft` 早已确立的"永远显示四段、不裁零位"惯例（未裁剪：`0天23时59分34秒` 这类恰好不到一天的情况也照常显示"0天"，跟拍卖行 `d:0` 的展示方式一致，不引入第二套裁剪规则）。新增 `formatDuration.ts::dhmsFromMs(ms)`（毫秒 → `{d,h,m,s}` 整数对象）给两处调用点用：`WorldMapPanels/hud.ts` 的 buff 行、`CityScene/modals.ts` 训练面板的加速提示行。只动这两个 key——世界地图行军列表的 `{remaining}s`、`world.occupying`/`world.occupyingMine` 的裸秒数不在本次截图反馈范围内，未改。

**护盾动画**：原实现（`WorldMapRenderer/city.ts` 的 `shieldFx` Graphics）只在 `refreshCityLayer` 被触发时重绘一次（拍板/缩放/~5s 行军轮询/`invalidatePool`），呼吸用 `Math.sin(Date.now()/450)` 算相位——但相机不动时压根没人再调 `refreshCityLayer`，所以呼吸实际上几乎不动，静止画面看起来就是一张贴死的半透明椭圆图。改法：把绘制逻辑抽成 `WorldMapRenderer/shieldFx.ts::drawShieldFx(g, geom, t)`，`t` 用 `WorldMapContext.shieldAnimT`（`lifecycle.update(dt)` 里逐帧累加的秒数，不用 `Date.now()`，跟其它倒计时/动画一样可测）；`city.ts` 的 `refreshCityLayer` 算出椭圆的局部坐标（`cx/cy/rx/ry/tp`，只随贴图尺寸/缩放变化）后缓存进 `ctx.shieldGeom`（`cacheKey → geom`），`lifecycle.update` 每帧遍历这个 map 用当前 `shieldAnimT` 重绘，不用重算贴图布局，开销可忽略（视口内同时存在护盾的基地本就是少数）。视觉上除了原有的呼吸椭圆（保留，测试仍 spy 这一个 `drawEllipse` 调用不变），加了两层新东西让它读起来像"场"而不是"贴图"：外圈一条慢速旋转的虚线环（跟领地边界同款手绘虚线语言，只是转起来）+ 四个绕环反向旋转、错相闪烁的小光点。基地移除/失去保护时清 `shieldGeom` 里对应 key，`destroy()` 里整体清空，避免残留指向已销毁 Graphics 的条目。

**验证**：`tsc --noEmit` + `npx webpack --mode production` 全绿；`vitest run --config vitest.ui.config.ts`（133 文件/1251 例全绿，含既有的 `worldMapShieldBubble.ui.ts`/`worldMapBuffRow.ui.ts`/`cityTrainTroops.ui.ts` 三个直接覆盖点，后两个的断言从 `.split('{sec}')` 改成 `.split('{d}')` 去匹配新模板前缀）。可视化核对：因为要看到真实 `protectedUntil` 需要拉起整条 worldsvc 后端 + 登录 + 入驻世界，成本远超这次纯前端视觉调整的量级，改用 `mcp__visualize__show_widget` 跑了一份跟 `drawShieldFx` 逐行对应的 canvas 版本（同样的三角函数/参数）做动画预览确认效果，未在真机截图——后续如果这层视觉再有反馈，用 [[worldmap-standalone-debug-render]] 记录的 `?worldmap&desk=N` 假数据套路能更快复现真实渲染路径。

## 2026-08-08：护盾特效借鉴 daydayup 的 additive-glow + 破碎闪光（用户提议）

用户提到另一个项目 `D:\daydayup`（PixiJS v8 俯视角射击 roguelite）的角色护盾效果不错，问能不能借鉴，同时给了前提——"如果性能耗费太大就算了"。

**先看 daydayup 怎么做的**：`client/src/game/fx/filters.ts::EnergyShieldFilter` 是一个自定义 fragment shader（Pixi `Filter`），套在角色贴图容器上做"轮廓光晕"（UV 距中心距离 `smoothstep` 出一圈环，`sin(uTime)` 调呼吸相位，`color.rgb += uColor*glow` 把颜色叠进贴图本身）；护盾破碎那一下是另一套东西——`FxController.flash()`，纯 `Graphics` 画 5 层同心圆叠加 `blendMode:'add'`，170ms 生命周期后销毁。

**能不能照搬**：不能 1:1 搬——那是自定义 Pixi `Filter`，每个套 filter 的对象要过一次离屏渲染目标（RTT）合成，这是 filter 机制的固定开销，跟 shader 本身轻不轻无关；本项目的护盾从来是 `PIXI.Graphics` 直接画（矢量描边/填充），没有、也不打算引入自定义 shader pipeline，为了这一个不大的椭圆光泡去接一条新的 filter 管线不值——这正是用户说的"性能耗费太大就算了"那一挡,所以 shader 本体没有借。

**借的是什么**：daydayup 的 shader 里"叠色进贴图"那部分没法在纯 Graphics 方案里等价（那是像素级的"给角色本身打光"，Graphics 只能"贴一层额外图形盖上去"），但另外两个思路是纯 CPU/矢量手法，能直接搬：① **additive 混合**（`blendMode:'add'`，daydayup 的 `flash()`/trail dots 用的手法，本项目 `GachaScene/reveal.ts` 的传说卡拖尾也已经在用同一个 API）——一层薄薄的半透明色，正常混合（`normal`）叠在纸色背景上看起来还是"半透明贴纸"，换成 additive 之后同样的颜色/alpha 会真的"发亮"，视觉上更像"能量场"而不是"多一层灰蓝色蒙版"；② **护盾破碎的一次性闪光**（daydayup 的 `shield_break` 同心圆爆闪）——本项目原来护盾到期就是悄无声息地消失，什么反馈都没有,加一个瞬间的"啵"一下的环形爆闪，玩家才能感知到"保护刚刚结束了"。

**实现**（`WorldMapRenderer/shieldFx.ts` 拆成三层）：
- `drawShieldFx`→拆成 `drawShieldDome`（原来的呼吸椭圆，`shieldFx` 子节点不变，保持 normal 混合——它是"玻璃罩"，不是"光"，跟纸感背景更协调；既有测试仍 spy 这一个 `drawEllipse` 调用，未受影响）+ `drawShieldGlow`（原来那圈旋转虚线环 + 4 个闪烁点，挪到新的 `shieldGlowFx` 子节点，创建时设 `blendMode = PIXI.BLEND_MODES.ADD`）。
- 新增 `drawShieldBreakFx`：3 层同心椭圆环，随 `age`（0~`SHIELD_BREAK_LIFE=0.4s`）向外扩散、线宽和透明度同步衰减到 0，挂在新的 `shieldBreakFx` 子节点（同样 additive）。
- 触发点：`city.ts::refreshCityLayer` 判断 `tile.protectedUntil` 已过期的分支里，如果 `ctx.shieldGeom` 里还留着这个 `cacheKey`（说明上一次重绘时还在保护中，这一次刚掉），就把当时缓存的几何形状塞进新的 `ctx.shieldBreakFx` map（`age:0`），`lifecycle.update` 逐帧给它加 `age`、重绘，超过生命周期就清空 Graphics + 删条目。
- 性能：额外开销只是——原来一层 Graphics 拆成两层（多一次 `clear`+ 重绘,同数量级的矢量指令，无新增采样/RTT）；破碎闪光是极低频事件（一个基地的保护期到期这件事本身几小时才发生一次）+ 400ms 生命周期到时即挂空，不会常驻。跟 daydayup 的自定义 Filter 比是同一件事"用更便宜的手法造类似的视觉印象"，量级上更接近它的 `flash()`（纯 Graphics + additive）而不是 `EnergyShieldFilter`（自定义 shader + RTT）。

**验证**：`tsc --noEmit` + `npx webpack --mode production` 全绿；`vitest run --config vitest.ui.config.ts`（134 文件/1255 例全绿，含 `worldMapShieldBubble.ui.ts` 四例——`drawShieldDome` 仍是唯一一次 `drawEllipse` 调用，未受拆分影响）。可视化核对：跟上一条一样，用 `mcp__visualize__show_widget` 做了跟新代码逐行对应的 canvas 预览（含一个手动触发"护盾破碎"的按钮），确认呼吸 dome + additive 发光环 + 破碎闪光三层叠起来的视觉效果，未拉起真实 worldsvc 后端验证。

**补测试**（用户要求，同日）：`worldMapShieldBubble.ui.ts` 新增一个 describe 块共 5 例——① 有效护盾在独立的 `shieldGlowFx`（`blendMode===PIXI.BLEND_MODES.ADD`）上画出 4 个 `drawCircle` 闪烁点；② 无护盾时 `shieldGlowFx` 同样一次 `drawCircle` 都不画；③ 两次 `invalidatePool()` 之间把 `tileCache` 里同一基地的 `protectedUntil` 从"未来"改成"过去"（模拟真实时间流逝/`tile_update` 推送），断言 `ctx.shieldGeom` 转移到 `ctx.shieldBreakFx`（`age:0`）且新出现的 `shieldBreakFx` 子节点也是 additive；④ 从未被保护过的基地两次重绘都不会误触发 break flash；⑤ 直接调用 `ctx.view.update(SHIELD_BREAK_LIFE + 0.1)`（同 `worldMapVignette.ui.ts` 已确立的"直接调 lifecycle mixin 方法"套路），断言 `shieldBreakFx` 条目在生命周期耗尽后被清掉。全部通过真实 `WorldMapContext`/`WorldMapRenderer`（非 mock 的 fake ctx），跟原有四例同一套 harness。

## 2026-08-08：进攻队伍选择器对"停留中"队伍的忙碌判定跟服务端不一致——攻击一个看着"空闲"的队伍却报 TEAM_BUSY（用户截图报告，账号 tao）

## 2026-08-12：加载遮罩改成"橡皮擦"式揭示，而不是瞬间消失

## 2026-08-17：拒马坐得太靠下 + 可占领前沿高亮太抢眼（用户截图反馈，账号 tao）

用户在世界地图截图上圈出两处：①两道拒马看着"掉出格子"，要求"稍微往上放点，使其看起来在格子中间"；②可攻打/可占领地块的绿色虚线高亮"太显眼了"，要"能让玩家一眼看到，但不能太抢夺焦点"。

**① 拒马纵向锚点（`tileGraphics/tiles.ts`）**。`placeBuildingSprite()` 一直把所有结构精灵的**底边**钉在 `hh * 0.72`（`hh` = 菱形半高 = `tp*ISO_RATIO/2` = `tp*0.25`）。这个系数对**高**建筑是对的——瞭望塔/箭塔从靠近下顶点的位置往上长，重心自然落在格心之上，读起来像"站在地上"。但拒马是**又宽又扁**的横向障碍（`BLOCKER_H = 0.22`，精灵高度 `tp*0.22` 对上半高 `tp*0.25`），同一个底边系数下整个剪影全部落在菱形的下半区，看着像从格子里滑出去了。

修法：`placeBuildingSprite()` 增加可选参数 `baseF`（默认仍 `0.72`，瞭望塔/箭塔不变），拒马单独传 `BLOCKER_BASE_F = 0.50`。扁平物件的**居中公式**是 `baseF = (tp*BLOCKER_H/2) / hh = BLOCKER_H / ISO_RATIO = 0.44`（精灵视觉中心正好落在格心）；取 `0.50` 而不是 `0.44`，是刻意保留一丝"略微靠前坐着"的接地感，同时已经读作居中。图集未就绪时的几何回退（交叉削尖木桩）也改用同一个 `blockerBaseY = hh * BLOCKER_BASE_F`，避免图集中途解码完成时路障在格子里**往下跳一格**。

**② 前沿高亮改成"角标"而不是整圈虚线（`WorldMapRenderer/fog.ts::renderOccupyFrontier`）**。旧画法是每个前沿格描一整圈绿色虚线：线宽 `max(2, tp*0.08)`、alpha `0.9`、dash `tp*0.16`/gap `tp*0.09`。前沿本来就是一条连成片的带子，于是满屏是一根贯穿整个视野的粗绿绳，压过了地图自己的墨线、建筑和行军令牌。

新画法保留 §4.1 那条"共边关系必须一眼可见"的设计意图，只换表达强度：
- 面色微微加强（alpha `0.10` → `0.13`），由**面**承担"到底是哪几格"的读取；
- 整圈虚线换成**四角短角标**（新增基元 `tileGraphics/primitives.ts::drawPolygonCornerTicks`，每个顶点朝两条邻边各画一段占边长 `tickFrac` 的短须，`tickFrac` 内部封顶 0.5 以免两端相接退化回整条边）：线宽 `max(1, tp*0.022)`、alpha `0.45`、`tickFrac = 0.13`——约为旧线宽的 1/3、旧 alpha 的一半。相邻前沿格共享顶点，角标会汇成一串小十字，正好把带子的走向标出来，而不需要任何长笔画。

**验证**：`tsc --noEmit` + `tsc -p tsconfig.test.json --noEmit` 全绿；`vitest run --config vitest.ui.config.ts test/ui/`（196 文件 / 1735 例）全绿，其中 `worldMapDrawPrimitives.ui.ts` 新增 3 例护住 `drawPolygonCornerTicks`（每顶点两段短须且起点必须落在顶点上、`tickFrac` 封顶 0.5 时两端只到中点不重叠、退化多边形不画）。可视化按 [[worldmap-standalone-debug-render]] 走：worktree 里起 `start:e2e`（临时 launch 配置 + `client/node_modules` junction），Playwright 调 `window.__nwE2E.views.showWorldMap()`（reject-fast `worldApi` stub），种一块 5×5 己方领地 + 一排拒马 + 瞭望塔/箭塔各一座作高度对照，L1/L2 各截一张，并把改动 `git stash` 后截了一张 before 做逐像素放大对比——拒马确认已居中、前沿带在 L1/L2 都仍一眼可辨但不再压过地图。验证用的 `shot.mjs`/`crop.mjs`/PNG 与 `WorldMapScene.ts` 里的临时 `__NW_DEBUG_WM_CTX` 钩子已全部删除（`test/no-debug-hooks-in-src.test.ts` 复跑绿）。

## 2026-08-19：删掉散布式「关隘」（familyKeep）地块——3.3% 的地图被门楼糊成一整片砖墙（用户截图）

用户截图圈出大世界里一大片"看起来真丑"的东西：一个巨大的菱形区域被同一张手绘城门楼（`art/slg/slg-map/building_keep.png`：拱门+闸栅+城垛）重复铺满、互相压盖成一面连续砖墙。

**定位**：那不是一个建筑，而是**成片的 `familyKeep` 地块各画了一座自己的门楼**。渲染侧逐格贴图（`client/src/scenes/worldmap/tileGraphics/tiles.ts`：`familyKeep → building_keep`，`placeBuildingSprite(..., tp * 1.3, ...)` 比格子还大 30%，相邻格必然重叠）。生成侧的病灶是**平滑 value-noise 过阈值**：

```ts
// 旧 server/shared/src/slg/mapgen/tileGen.ts
const keepNoise = valueNoise(x, y, SLG_GEN.keepFreq /* 1/22 */, seed ^ 0x0222);
if (keepNoise > SLG_GEN.keepThreshold /* 0.86 */ && distToCap > SLG_GEN.keepMinDistRatio) → familyKeep
```

平滑噪声的等值区天然是连通团块，而这个类型一直被文档描述为"稀疏的战略点"。在现役 1500×1500 地图上实测（直接跑 `proceduralTile` 全图扫描 + 四连通 flood fill，worldId `w1`）：**74,124 格关隘（占全图 3.29%），472 个连通团块，最大团块 1,745 格 / 包围盒 68×56**。同一份源码里 `strongholdThreshold` 的注释（§19.5、`ECONOMY_NUMBERS §13-SLG-STRONGHOLD`）早就把这个坑写清楚了——险地正是因此从 value-noise 改成逐格 Bernoulli 哈希，关隘漏改了。

**同时确认它已经没有玩法可言**（用户追问"这个关隘有什么用处"后逐路径核对）：

- 产出：等级被强拉到 `max(level, 9)` → `100 × 9 = 900/h`，全图最高档之一；
- 守军：`npcGarrison(9) = 1080`，比同区普通地略硬，和险地的 11800 差一个数量级；
- 占领方式：和普通中立地**完全一样**（占领/扫荡/停留就地占领），`startMarchValidation.ts` 只特判 stronghold/bridge/plankway，关隘不须攻城；
- **不控制通行**——"免费关隘"在 gate→bridge/plankway 迁移（§3.1 统一通道机制）里就废了，过阻挡带只认桥/栈道；
- 无夺取奖励（险地有资源+材料掉落）、无特殊守军/耐久/加成、客户端点开连专属说明文案都没有（走通用中立地分支）；
- 名字里的 `family` 是更早版本的遗留，与家族/宗门无关。

即"一块产量拉满、守军略强、长得像城门的普通资源地"，却铺满 3% 的地图。

**处置（用户拍板：先删，后期有新需求再单独设计）**：

- 删掉 `tileGen.ts` 里的散布式 keep 判定分支——这些格子直接落到下面的 resource/neutral 分类，仍然可占领，只是按所在环该有的资源等级产出（不再被强拉到 9 级）。
- 删掉 `SLG_GEN.keepThreshold` / `keepFreq` / `keepMinDistRatio`（全仓库无其它读者）。
- `familyKeep` **类型本身保留，但语义收窄为「城池地面」**：程序化的州府/分级城节点锚点格（各 1 格）+ 地图编辑器城池占地的 rasterize 结果（`mapEdit.ts`）。`TileType` 注释、契约枚举、渲染映射均不变，避免动契约。
- 未来若要真做"咽喉点"玩法，注释里明确要求用逐格 Bernoulli 哈希（照 `strongholdThreshold`），**不要**再用平滑噪声阈值。

**副作用（已知并接受）**：①地形是种子确定性算出来的，同一 worldId 的这些格子类型/等级会变（已占领记录、行军、建筑不受影响，只是脚下地格的类型/产率变了）——按用户口径，现役世界接受这次地形漂移；②高等级地块供给略降（原先 3.3% 的强制 9 级地没了），经济侧属于"少了一批白给的高产地"，未单独重跑经济核验。

**遗留（本刀刻意不做，另开任务）——✅ 已于同日下一条修掉**：地图编辑器发布（`rasterizeMapEdits`）会把城池 N×N 占地整块刷成 `familyKeep`，而客户端城池精灵层（`WorldMapRenderer/city.ts` 的 `cityNodes()`）只读程序化的 `allCityNodes()`——设计师新增/挪动的城不会跟着挪精灵，其占地格反而会再次逐格盖门楼、复现同样的砖墙。正确修法是让精灵层读发布后的城池节点，属另一件事。

**验证**：`server/shared` vitest（含新增回归用例"familyKeep 只在州府/分级城锚点格出现、全图无团块"——全图 225 万格扫描，断言坐标集合与 `allCityNodes()` 完全一致）+ `tsc --noEmit`；可视化用 map-editor（`tools/map-editor`，webpack alias 直读 `server/shared/src`，改完即时生效）改前/改后同一坐标截图对比。

**补测（同日追加，3 例）**：①同一 familyKeep 不变式再跑 3 个种子（团块严重程度随种子摆动过：一个世界 74k 格、另一个 90k），用 stride 3 抽样——采到 1/9 的格子，任何 ≥3 格宽的团块都躲不过，精确集合相等仍只在一个种子上跑，避免多次全图扫描拖慢用例；②**据点（stronghold）保持逐格 Bernoulli 孤立点**：600×600 窗口内密度落在 0.08%–0.30%、最大四连通簇 ≤4（实测各种子 0.11%–0.20%、最大簇 2）。这正是被删的 keep 分支违反的性质，而此前据点侧也从没断言过；注意门槛是"簇要小"而不是"零相邻"——随机逐格场本来就会偶尔出现相邻对；③`rasterizeMapEdits` 把顶档城池刷成实心 9×9=81 格 familyKeep，钉住"城池地面"语义，同时把上面"遗留"那条的现状写进用例（真要修就必须自觉改这条期望）。三条都反向验过：临时把旧噪声分支塞回去、以及把据点门换成平滑噪声，确认对应用例确实变红，之后精确撤回（未用 `git checkout`，避免连累共享检出里别人的未提交改动）。

## 2026-08-19：城池节点改为「发布数据」——精灵层不再从种子重算，`familyKeep` 也不再逐格盖门楼

**背景**：上一条（散布式 `familyKeep` 删除）末尾"遗留"列的正是这件事。当时的状态：

- 地图编辑器可以拖城（`tools/map-editor` City 工具），发布时 `rasterizeMapEdits()` 把每座城的 N×N 占地整块刷成 `familyKeep`（世界中心是 `center`），进模板 → 开服克隆进世界基线 → 客户端确实能读到挪过去的**地面**；
- 但客户端城池**精灵**层（`WorldMapRenderer/city.ts` 的 `this.core.cityNodes()`）读的是 `allCityNodes(worldId)`——纯种子推导。于是拖过的城：**地面挪了、城堡没挪**，新位置是一片空的城池地面，旧位置是一座浮在普通地上的城堡；
- 更糟的是那片新占地的每一格都会各画一座 `building_keep` 门楼（`tp*1.3`，相邻必然重叠），正是上一条刚删掉的砖墙效果——**发布一座城就复现一次**。

还查出一个此前没人注意的第二重错位：模板是用 **`proceduralTile(templateId, …)`** 生成的（`generateTemplate`），也就是种子是 **templateId**；而客户端算 `allCityNodes(worldId)` 用的是**世界自己的 id**。所以只要 `worldId !== templateId`，哪怕设计师**一座城都没拖**，地面和精灵也对不上。

**处置**：把城池节点从"客户端本地算"改成"服务端发布数据"，一条链打通。

- **@nw/shared**
  - `proceduralTile()` 拆出 `proceduralTileIgnoringCities()`——去掉三个城池地面分支（世界中心块 / 州府锚点 / 分级城锚点）后的那份分类，即"这格底下如果没有城，该是什么地形"。
  - 新增 `proceduralCityGroundTiles(worldId)`：列出 `proceduralTile` 会判成城池地面的全部格子。注意其**不对称性**——只有世界中心铺满 9×9，州府/分级城各只有 1 格锚点（其余占地是精灵盖上去的视觉，不是地格）。派生自 `allCityNodes()`，不会跟节点表漂移；回归用例把它与 `proceduralTile` 对齐锁住。
  - `rasterizeMapEdits()` 新增 `opts.citiesAreComplete`：声明"传进来的 `cities` 是完整城池图层"，据此把**没有城站在上面的**程序化城池地面格还给地形（`proceduralTileIgnoringCities`）。**必须显式开启**，不能默认——传进部分列表（比如单测里只放一座城）时默认开启会把没提到的城全抹掉。三趟覆盖顺序：①腾空的锚点还给地形 → ②画笔地形 → ③城池占地（最高优先，§6.2 不变）。编辑器的两个调用点（实时预览 `render/baseMap.ts`、发布 `ui/publish.ts`）必须**同样**开启，否则 WYSIWYG 断裂。
  - `parseCityNodes()`：不可信节点列表的校验器（kind 白名单、坐标整数且在图内、`footprint` 为正奇数——占地以节点为中心，偶数边长没有中心格），供 admin 写入端复用，与编辑器自己的 JSON 导入共用同一套"合法节点"定义。
- **worldsvc**
  - `MapTemplateDoc.cities?` / `WorldDoc.cities?`（约 64 个节点，整存整取，不按行分片）。
  - `MapTemplateService.getCities/saveCities`；`cloneActiveTemplateInto()` 顺手把节点表克隆到 `WorldDoc.cities`——**总是写**，模板没发布过节点表时回退 `allCityNodes(templateId)`（即该模板地形实际生成用的那套），这一步就把上面第二重错位一并修掉了。
  - 内部 endpoint `GET/PUT /admin/world/map-templates/{id}/cities`。
  - 读路径 `MapService.getCities(worldId)`：`WorldDoc.cities` → 回退 `allCityNodes(worldId)`（2026-08-19 之前开的世界 / 无激活模板的世界，行为与从前一致）。
  - **随 `POST /world/enter` 一起下发**（`cities` 字段，`openapi-world.yml` 加 `WorldCityNodeView`）而不是单开路由：精灵层每次进地图只需要一次，跟 season/nations 同频，省一个 round-trip。
- **admin**：`clients/world.ts` + `service/mapTemplates.ts` + `httpApi/slgRoutes.ts` 各加一对 get/save 代理（`slg.map.view` / `slg.map.manage`，写操作走 `audit()`，新审计动作 `slg.map.template.cities`）。
- **tools/map-editor**：`api.saveMapTemplateCities()`；Publish 在上传 tile diff 之后**总是**上传整份节点表——即使 tile diff 为空（tile 只是城下面的地，节点表才是精灵的依据），所以原来的"没有可发布内容"提前返回和 `status.nothingToPublish` 文案一并删掉，状态行改为同时报格子数和节点数。
- **客户端**：`WorldMapContext.cityNodes`（服务端列表，未到达时为 null）→ `WorldMapRenderer/core.ts` 的 `cityNodes()` 优先返回它，`allCityNodes(worldId)` 退为兜底（进图前几帧 / 离线 / 测试 fixture）。

**顺带拍板：`familyKeep` 的逐格 `building_keep` 门楼整体删除**（客户端 `tileGraphics/tiles.ts` + 编辑器 `render/tileGraphics.ts` 两份同步，SLG 地图渲染 parity）。理由：

- `familyKeep` 现在只剩"城池地面"一种语义，而城池的美术就是城池层那**一个**按 footprint 缩放、按 plot 菱形裁切的精灵；占地格再各画一座门楼，画的是精灵**底下**的东西；
- 程序化城池只有锚点 1 格，那座门楼恰好被精灵盖住 → 看不出来；发布过的城是整块 N×N，于是每格一座、连成砖墙 → 正是上一条刚删掉的画面。也就是说这个 stamp **没有一种情形是有用的**，只有一种情形是坏的；
- `center`（世界中心）本来就没有 stamp，删掉后城池地面两种类型行为统一。

资源母题的抑制**保留**（`familyKeep`/`center` 仍算 `hasBuilding`）：城池地面照旧带 biome `resType`，但城堡底下摆一堆资源图标同样没有意义。`building_keep` 图集帧留在 `building_atlas` 里不动（日后真做咽喉点玩法可复用），loader 注释标注"当前无人读取"。

**已知未做（刻意）**：`_inCityBackBands` 的"城池背面资源等级封顶"（`RESOURCE_LEVEL_CAP_NEAR_CITY`）仍按**程序化**城池位置算，所以拖走的城会把旧封顶留在原地、新位置不封顶。那是等级分布的产物（顶到 5 级 vs 环表自己的 roll），不是渲染错位；真在意的格子按 `cities.ts` 里那条注释的口径直接在编辑器里手绘。

**验证**：`server` 全量 `tsc -b` + `client` / `tools/map-editor` `tsc --noEmit`；`server/shared` vitest（新增 `proceduralCityGroundTiles` / `proceduralTileIgnoringCities` / `parseCityNodes` 用例，以及 `rasterizeMapEdits` 的 `citiesAreComplete` 一组：默认关闭时不碰未提及的城、原样发布节点表不产生腾空锚点、拖走的分级城锚点还给地形、拖走世界中心整块 9×9 还给地形、画笔地形仍压过还原、城池占地仍压过画笔）；`tools/map-editor` vitest（i18n 占位符 fixture 补 `cities`，并把此前漏测的 `status.published` 一起纳入）；worldsvc vitest；map-editor 实机截图核对城池占地不再有门楼砖墙。

## 空地占领：攻城值随携带兵力缩放 + 5 级以上空地「数学上不可破」修复（2026-08-19）

玩家报告（账号 `tao`，s2-0）：**打 3 级空地连输**，"队伍配置已经很高了"。把生产库 `sieges` 里存的 replay 输入逐 tick 原样重放，两场败仗结束时敌方基地只剩 **0.248/120** 与 14.2/120 血——差一丝没拆掉，不是被守军碾压。顺着这条线量出三件事：

1. **兵力被截断**：`Unit` 构造函数 `hp = min(兵力, 蓝图单兵血量)`，mara 124 兵→44.8 血、infantry 249 兵→67 血；tao 的 2038 名义兵力入场只剩 1010。

## 分兵上限补服务端强制 + 把「血量 / 攻城值」两种兵力在 UI 上分开（2026-08-19，ADR-069 收尾）

ADR-069 那条记录末尾留了两处已知遗留，本次一起做掉：

**① `distributeTroops` 服务端真的校验 `troopCap` 了。** 之前只有客户端 stepper/一键分兵在守，服务端函数自己的注释却写着「enforced on every way IN」。ADR-069 之前后果有限（超出单兵血量上限的兵力在战斗里是惰性的），之后就变成「一张卡堆满整池兵 = 一击拆任何基地」。现在服务端按 `cardTroopCap(card)`（新加到 `@nw/shared/cards`）校验，超限抛 `CARD_TROOP_CAP_EXCEEDED`（新错误码，客户端 `errorMsg()` 已映射为可读文案），并把同一条界限重复写进 update 的过滤器，堵掉「两个并发请求各自通过 JS 侧检查」的竞态。战后结算只会调低 `currentTroops`，所以入口只此一处。客户端保留自己的 `CardDef` 镜像表，于是新增 `cardDefsSharedParity.test.ts` 把两张表的带兵上限逐卡逐级钉死——漂移会让玩家撞上「按钮给的数服务端不收」。

**② 「哪些兵变成血量、哪些兵只买攻城伤害」现在看得见。** 引擎 `hp = min(兵力, 蓝图单兵血量)`，而卡的带兵上限跟蓝图血量完全是两个数（1 级李闯带 200 兵、却只是个 60 血的步兵；1 级陈守带 100 兵、盾兵蓝图有 240 血）。编队界面的兵力条原来是一根单色条，两种情况长得一模一样。现在条子分两段：血量段沿用原来的绿/琥珀/红，超出单兵血量上限的部分画成紫色（刻意跳出「满不满」的色阶，读作"另一种兵"）。花名册详情面板在超限时多一行「其中 N 兵超出血量上限，只算攻城值」，不超限则完全不显示。

测试：`card-slg.e2e.test.ts` +5 例（超限拒绝且不扣池、正好填满再多一兵被拒、按卡分别计算上限 + 多卡分配全有或全无、并发不能合谋越界、库存里没有的卡 id 直接拒）、`cardDefsSharedParity.test.ts` 5 例、`defenseEditorTroopBarSplit.ui.ts` 5 例（读 `graphicsData` 断言两段的颜色/宽度/衔接）、`cardDetailSiegeValue.ui.ts` +2 例。

## 2026-08-25 兵力上限曲线重调（ADR-075）：练兵场从「可跳过」变成主线，训练队列去掉一半死槽

用户从主城训练面板的截图问了一句「训练士兵的队列有上限吗」，答案挖出两条互相独立、但同源的数值脱钩。

**① 训练队列一半的槽位是死的。** 槽位能起作用的上限是 `ceil(troopCap / TROOP_TRAIN_BATCH_MAX)`——再多一槽也占不到，因为批次会先被 `trainTroops` 的 troopCap 校验拒掉。2026-07-22 把 `TROOP_TRAIN_BATCH_MAX` 从 500 提到 5000（旧档位点满一次队列要点几十次），这个天花板就从 40 槽塌到 4 槽，可 `2 + floor(drillYard/2)` 的槽位曲线没跟着改，满级仍发 7 槽：**3 个永久死槽**。截图里那个「最大 +0」其实是撞了兵力上限而不是槽位满，但面板没显示槽位占用，两种情况在 UI 上长得一样。

**② `troopCap` 的成长曲线小到没有升级动力。** ADR-048 把 `TROOP_CAP_BASE` 提到 10,000、`DRILL_TROOPCAP_STEP` 留在 1,000，于是练兵场整条 10 级曲线只值 **2×**（10,000 → 20,000），首级只值 +10%——而它是兵力池成长的唯一来源。用户拍板：基数腰斩到 5,000、每级提到 1,500，满级不变（20,000），曲线变 **4×**、每级 +30% 基数。槽位曲线定 **1 / 2 / 3**（L0–3 / L4–9 / L10），刻意不超过天花板（仅 L0 持平），于是每槽都有用、且「空仓填满」在任何等级都**不超过两次上线**（L0 一批就满，1 次；L1 起每级 2 次）。

**没跟着改的，都是刻意的。** 单批 5,000 保持不动——让它跟着 troopCap 涨会立刻把死槽变回来（满级 10,000/批就只需 2 槽），练兵场的后期收益走 `drillTrainMult`（每级 -8% 时长）而不是更大的单批。险地/关隘守军（11,800 / 10,350）也不动，于是 PvE 门槛从练兵场 L1/L2 后移到 **L4/L5**：这是目的而非副作用，用户要的「升级动力」正好由这两个解锁来兑现（「4 到 5 级很快的」）。`GARRISON_PER_TILE` 也不动，新号能占的格子从 20 减到 10，「新手期变弱没问题」。门槛用 `strongholdCombatRun.ts` 实跑确认，不是推算——顺手把脚本里硬编码的 4 级扫描窗口放宽到 `DESK_MAX_LEVEL`，否则新门槛 L5 会掉在窗口外、脚本自己报「opens by drillYard+?」。

**落地时才浮出来的真问题：`troopCap` 是持久字段。** 它只在建造完工（`applyDueBuilds`）时按公式重算，不是每次读都算。所以改公式是一次**数据**变更：放任不管，存量号会卡在旧的存储值上，直到下一次练兵场升级完工才重算——而新公式在 L<7 时**低于**旧公式（旧 `10000+1000L` vs 新 `6500+1500L`），也就是「升级练兵场反而兵力上限变小」。对 L0–L6 的每一次升级都成立，不是边缘情况，而且是一次成长重调最难看的读法。改成 boot 迁移 `migrateTroopCapRetune` 一次性给所有人重算并把 `troops` 夹进新上限（一次性掉兵，用户已认可；数值仍标 DRAFT）。用 `$expr` 只命中「存储值与公式不符」的文档，所以幂等、不需要记账位，新世界天然是 no-op。

**顺带钉死的两条不变式**（都是这轮踩到才发现原来只是「恰好相等」）：`SATCHEL_CARRY_STEP` 从字面量 `1000` 改成直接等于 `DRILL_TROOPCAP_STEP`，D-CITY-9 的「满级书包单队能带满满级兵力池」从此按构造成立；shared 单测新增一条全等级区间断言「任何等级都不发放 troopCap 填不满的槽位」，把这类「批次上限一动、槽位曲线就脱钩」的漂移拦在测试里而不是注释里。

**UI**：训练面板补一行 `city.trainQueueStatus`（三语）`队列 {n}/{max} · 在训 {training} · 可训 {left}`，槽位满或可训为 0 时转红。`可训` 是 `cap - troops - 已排队`，直接对上「最大 +N」的数字——原来那行「兵力 10880/20000」看起来还有 9120 的余量，实际早被在训批次预定光了。

测试：`econ-sim` 18 例（门槛等级改为派生常量 `STRONGHOLD_OPEN_DRILL_LEVELS`/`CROSSING_OPEN_DRILL_LEVELS`，扫描从常量派生 + 断言关隘门槛严格小于险地、门槛下一级仍必败）、`@nw/shared` city-buildings 15 例、`worldsvc` 全量 e2e（新增 2 例迁移：陈旧 cap 重算并夹兵 / 已正确时幂等不动 rev；`city-training` 新增练兵场加槽用例；`teams` 的书包边界用例改为从常量派生所需等级——原来硬编码的 `satchel: 1` 在新步长下不够了，正是这类字面量会静默失效的例子）、client UI 16 例 + i18n 6 文件。

### 补测（同日）：给 ADR-075 补 5 条不变式测试，写测试的过程里抓出 3 处自己写错的说法

上面那批改动的测试都是「这次改对了吗」，缺的是「以后被改坏时会不会有人知道」。补了 5 条，全部按「先证明它在旧状态下会红」的方式验过：

1. **`troopCap` 逐级严格递增**（`city-buildings.test.ts`）。对 `base + step×level` 看着像废话，但它正是本轮真实事故的公式层守卫——`troopCap` 是持久字段，旧曲线存下来的值比新曲线算出来的下一级还大，于是升级降上限。以后任何 step≤0、非线性档位表、或给公式加个 clamp，都会先在这一行红。
2. **「空仓填满不超过 2 次上线」**（同上）。槽位买的就是这个「要回来几趟」，所以给它一个上界比描述它更管用；同时断言「L1 之后再投入不会比 L1 更费趟数」——后期比前期更肝正是本 ADR 要消灭的手感。
3. **PvE 门槛四条不等式**（`siege.test.ts` 新增 `PvE gate calibration invariants`）：新号打不过 / 满级打得过（**永不变成打不下**）/ 关隘严格轻于险地 / 满级书包单队投送量够破险地。第四条是 §13-SLG-STRONGHOLD.7 登记的那条「未建模耦合」——池子够但单队带不动时门槛实际不可开，而池子侧的不等式看起来仍然正常。
4. **完工建造永不降低已存 `troopCap`**（`city-buildings.e2e.test.ts`）。把 1 的公式层不变式钉在它真正发作的那一层（`applyDueBuilds`）：种一个旧曲线的陈旧 cap → 跑 boot 迁移 → 升一级 → 断言只增不减。
5. **迁移里两个 `$ifNull` 各有一条用例**（`card-slg.e2e.test.ts`）。`$troops` 那条早先就补了；这次补 `$buildings.drillYard`——缺 `buildings` 字段时 `$multiply` 出 null，cap 会被写成 null。

**为什么这批测试特别值**：③ 把回归有效性验到了历史事故本身——守军回滚到 .5 修复前的 360/200，用例①立刻红（`expected 10000 to be less than 1800`），也就是当年那个存续数周才被审计发现的状态。这套不等式此前**只有一个需要人主动去跑的脚本**在守。

**写测试的过程里抓出 3 处我自己写错的说法**（都已订正，值得记下来是因为它们全都同时进了源码注释和 3–4 份设计文档）：

- 「空仓填满在任何等级都**恰好** 2 次上线」——L0 的上限 5000 正好是一批，只要 1 次。真正成立的是**不超过** 2 次。
- 「有用槽位天花板 **2** 槽 @L0 升到 4 @L10」——`ceil(5000/5000)` 是 **1**，不是 2。
- 「阈值**刻意低于**天花板」——L0 是 1 槽 vs 天花板 1 槽，**持平**而非低于。（好在断言本来写的是 `<=`，代码和测试是对的，错的只是散文。）

三处都是我在基数还是 10,000 时算的数，改成 5,000 后没重算。这类「注释里的算术」不会被 tsc 或任何测试发现，除非把它写成断言——本轮 2 恰好就是那个断言，它红的第一次就是因为这个。

**顺带去掉一处三份实现**：写 ③ 的时候要拿关隘的生成等级，发现 `Math.max(2, SLG_MAP_MAX_LEVEL - 1)` 被开写在三个地方——`shared/slg/mapEdit.ts` 的私有 const、`econ-sim/strongholdCombat.ts`、以及 `siege.ts` 注释里的散文「currently 9」。把 mapEdit 那个导出成 `CROSSING_TILE_LEVEL`，另两处改为引用（注释那处保留散文但已标明来源）。跟本轮主题同一个形状：一条规则有几份拷贝，就有几份各自变陈旧的机会。

**另一个自己踩的坑，值得记**：验证「④ 在没有迁移时会红」时，第一次跑出来是**绿的**——因为我把 `core.ts`/`city.ts` 从 `.bak` 恢复后**没有重新 `npm run build`**，worldsvc 解析 `@nw/shared` 走的是 `dist/`，测的还是旧常量（`troopCapFor(L4)` 仍返回 14000，于是断言"恰好"成立）。这正是 [`claudedocs/worktrees.md`](../../claudedocs/worktrees.md) 里写的「改完 .ts 不 build，测试照样全绿，等于验证了个寂寞」。重建 dist 后立刻红成预期的 `expected 14000 to be 11000`。**在 worktree 里做"退回旧状态证明测试会红"这类实验，每次改完 shared 源码都必须重建 dist，否则整个实验无意义。**

## 2026-08-30：选中基地/城池只高亮 1 格 → 高亮整块地皮；「行军列表」重做成「队伍信息」（用户截图反馈，账号 tao）

用户截图圈了两处：①点中基地时，黄色菱形落在建筑内部某一格上，看起来像个位置画错的记号；②右上角「行军列表」按钮，要求改成「队伍信息」，把**所有**队伍的状态放进去，点一行直接跳到那支队伍所在位置，在家的队伍跳回基地。

### ① 选中高亮：要么不画，要么画满 9 格——评估后取"画满"

用户给了两个选项。判定**画满整块地皮更好**，理由不是美观而是"高亮说的话得跟规则一致"：基地是 ADR-025 的不可分割 3×3、野外城池是 ADR-034 §3 的 N×N（3×3 到 9×9），进攻打的是整块地皮（`targetFootprintCells`）、连地判定看的是它的**外周**、一个角格也无法被单独占领——下游每一条规则都把它当一个整体，只有这个记号把它当成 9 格里的某一格。"不画"则丢掉了点击反馈本身（触屏上误点很常见，弹出的菜单是唯一线索）。

**实现上没有"画 9 个菱形"这回事**：等距投影下 N×N 方块的并集本身就是一个 N 个格宽的菱形，所以还是**一个** `diamondPath(tp * size)` 画在地皮锚点上——不多一条线，边界正好压在瓦片美术自己画出的地皮边上。新增 `worldmap/logic/selectionFootprint.ts::selectedPlot()`：基地的锚点靠"扫描点击格自身 3×3 邻域、找那个四邻居也都是 `base` 的格子"反推（`WorldTileView` 没有锚点字段，跟 `attackFootprintCells`/`isBaseAnchor` 同一套判据）；城池走 `cityNodeCovering`（`familyKeep` 与世界中心的 `center` 两种地皮类型都认）；两者都在**解析不出来时退回单格**（视野缺口下宁可少画，也不猜一块别人的地）。

**多格时不填色**：overlay 画在 `cityLayer` 之上，单格上几乎看不见的 0.15 黄色水洗，铺到 9×9 首府上就是把整座建筑染了一层黄。多格只留描边（并加粗到 3px），单格维持原来的描边+淡填充。

### ② 「行军列表」→「队伍信息」

改名只是表层，真正的问题是**旧列表只能显示"正在路上"的队伍**：占领倒计时中的、野外停留/驻扎的、受伤的、以及什么都没干待在家里的队伍，在地图上**没有任何一行能代表它**——一个号称回答"我的部队在干嘛"的列表，只回答了其中少数几支。

- **行来源换了**（新增 `worldmap/logic/teamStatus.ts::buildTeamRows()`，纯函数、`now` 由调用方传入）：先按**队伍槽位顺序**每支编队一行（行军中 / 返回中 / 占领中 / 野外停留 / 野外驻扎 / 受伤 / 驻军在家），再把**没有 `teamId` 的己方行军**（散兵占领、按兵力池派的增援）各补一行——它们不是队伍，但确实是可撤回的部队，而旧的行军列表是**唯一**能撤回它们的入口，不能顺手弄丢。按槽位排序还顺带解决了"一条行军落地、整个列表在手指底下重排"。
- **状态词汇刻意复用 `CityScene/teamRow.ts` 的同一批 i18n key**（`world.team.marching`/`occupying`/`stationedIdle`/`garrisoned`、`city.military.teamIdle`、`roster.injured`）——两个界面描述的是同一批队伍，不该有两套叫法。优先级也照抄那边：**行军压过 station/occupation**（撤回途中三份文档并存，否则会闪一下"野外驻扎"再自我更正成"行军中"）。
- **点行跳转**：跳到该队伍**当前所在位置**——行军中跳目的地、占领/驻扎跳那块地、在家跳 `mainBaseTile`（用户明确要的那条）。行的命中矩形**在动作按钮处截止**，"跳过去"和"撤军"不抢同一片像素。
- **动作按钮**：行军 → 撤军；返回中 → 立即回城（付金币）；野外驻扎/停留 → 撤军（`doRecallStationed`）。占领倒计时**不给按钮**——`cancelOccupation` 是"驻守部队全部作废、不退兵"的不可逆操作，`TeamsScene` 那边是带二次确认的，不该在一个一行高的 HUD 行里给一个裸按钮。
- **徽章文案**：`队伍信息 (在外/总数)`。总数只在 `GET /world/teams` 落地后才显示——只按行军数推算会对一个有 5 支队伍的玩家说"你有 1 支"。
- **数据获取**：`teams` 是懒取的（`WorldMapNet.refreshTeams`），入口 `loadData` 之后**不 await** 地补一发（不塞进 `/world/enter`，那是 P1-5 特意压成一次往返的路径），展开面板时再拉一次（编队只在城内改，地图这边收不到任何推送），`refreshMe` 之后也跟一次（会触发它的那几个 overlay 正是能改编队的）。状态本身仍由既有的 marches/occupations/stationed 推送驱动，没有新增轮询。

### 布局：先量后排，不写死宽度

## 2026-09-02：地块弹窗——主城格不再显示地块资源，以及 showModal 长出图标槽（用户截图反馈）

用户截图圈出盟友主城弹窗里的「金属 · Lv.3」和两个纯文字按钮，问了两件事：建筑格是不是就不该显示地块信息；能不能给「移动并驻扎」「坐标」这类关键信息在文字前面加图标。

### ① 主城格的资源行是错信息，不只是多余

判定标准不是「重复/冗余」，而是**它说的话跟服务端的产出规则相反**：`@nw/shared` `slg/march.ts` 的 `tileYield()` 第一行就是 `if (type === 'base') return { ink: RESOURCE_YIELD_BASE }`——主城格底下埋的那个 `resType`/`level` **完全不参与产出**，主城一律按固定墨水速率出产。所以「金属 · Lv.3」宣传了一份不存在的产能。更糟的是那个 `Lv.3` 是**被埋掉的资源地块**的等级，跟它上一行的「耐久 2300」毫无关系——耐久走的是 `baseDurabilityMax(wall 等级)`（`300 + 200×wall`，截图里的 2300 = wall 10），两个数字并排读起来像同一套等级。

修法：`resLevelLine()` 加一条 `if (tile.type === 'base') return null`，一处覆盖我的/盟友/他人三个分支。**空出来的位置换成主城自己的等级**（新增 `world.baseLevel`），数据取 `tile.deskLevel`——`core/map.ts` 的 `tileDocView` 无条件下发它，不按归属过滤，所以盟友/敌方主城同样能显示。

`deskLevel` 顺带解决了「锚点 vs 环格」：3×3 里 8 个环格是 `type:'base'`、`level: 1`、无 `resType`/`deskLevel` 的占位 doc（`core/spawn.ts` `baseTileDocs`），只有锚点带 `deskLevel`。所以「有 `deskLevel` 才画等级行」这一条判据，正好让环格什么等级都不显示，而不是显示一个跟一格之外的锚点自相矛盾的 `Lv.1`。

### ② `showModal` 的图标槽

`WorldMapPanels/core.ts` 的 `showModal(lines: string[], buttons: {label}[])` 之前是纯文本，于是地块弹窗是整张世界地图上唯一没有任何图形语言的地方（顶栏产出、兵力/领地卡片、拍卖/商城/回家按钮全都有图标）。而且有 8 处 emoji 混在本地化字符串里充当图标（🗼🏹🚧⚠📄🔩）——emoji 走的是系统字体而不是游戏的手绘墨线，微信/iOS 上甚至不保证同一个字形。

新增 `WorldMapPanels/modalLine.ts`：`ModalLine = string | { text, icon }`、`ModalButton = { label, action, disabled?, icon? }`，加 `modalLineText`/`buildModalGlyph`/`coordLine`。**字形词表是两半的**：

- `IconKind`（`render/icons` 的墨色表/页签表）——运行时染色，纸底和深色按钮上都能用。
- `{ res }`——世界图集里的五张资源母题（`res_ink`…）。手绘黑线、**不许染色**（`resAtlasLoader` 的契约），所以**只给信息行用**；`ModalButton.icon` 特意只收 `IconKind`，让「往深色按钮上放资源母题」成为编译错误而不是渲染事故。图集是懒解码的，没到位时 `buildModalGlyph` 返回 `null`，该行按无图标排版，不画空框。

排版：信息行由「居中单个 label」改成「图标+文字整组居中」（无图标的行结果与旧版逐像素一致），图标在 label 的整体高度上居中——绝大多数带图标的行是单行，少数会折行的（说明/确认文案）当成项目符号读更自然。

**按钮图标有一道宽度门禁（`btnW >= 200`）**：满配的己方地块菜单有 9 个按钮，每列被挤到约 165px，`移动到此（停留）` 这种标签本来就已经折成两行，再花 34px 给图标会顶成三行、撑破 84px 的按钮高度。所以窄列不画图标、维持现状。**这是把一个既有的排版问题暴露出来了，不是这次引入的**——真正的出路是把那批标签缩短（有图标之后 `移动到此（停留）`/`移动并驻扎` 可以只留 `停留`/`驻扎`），属于产品决定，留给后续。

## 2026-09-02：占领倒计时结束不发 `march_update` → 五支队伍在客户端永远「忙」，弹窗还甩了一句假话（用户截图反馈，账号 tao，线上）

**先取线上事实**（Atlas 只读脚本，`[[game-vps-access-2026-07-14]]` 的 `docker cp` 套路）：`playerWorld s2-0` 五支队伍各 12 张卡、`cardState` 携带兵力 1700–2525，`marches`/`occupations` 都是 **0 条**，`stationed` 5 条全是 `mode:'idle'`、`sinceAt` 集中在 13:48:08–13:48:22。也就是说**服务端侧五支队伍全空闲**，`showTeamPicker` 的 busy 过滤器按这份数据本该列出五支队伍。差异只可能出在客户端缓存。

**决定性证据在 gateway 日志**：13:43:09–13:43:22 是五次占领到达（`march_update` + `siege_result` + `tile_update` 三连），5 分钟后（`OCCUPY_HOLD_SEC`）的 13:48:08–13:48:22 只剩 **五条 `tile_update`，一条 `march_update` 都没有**。

**根因（服务端）**：`combatSiege/occupation.ts` 的占领结算把 `OccupationDoc` claim-delete 掉、翻转地块归属、写下 `StationedDoc`，然后**只**推 `tile_update`。而客户端世界地图重新拉取 `marches`/`occupations`/`stationed` 三片状态的**唯一**触发点就是 `march_update`（`worldmap/net/push.ts` 的 `applyMarchUpdate → refreshMarches`；原来那个 5 秒轮询在 comm-audit-2026-07-27 P1-2 里被删掉了，理由正是"push 已覆盖每一次状态变化"）。`tile_update` 的处理只重拉地块。于是**每一个结算完的占领都永远留在客户端的 `ctx.occupations` 里**，它点名的队伍在 `busyTeamIds` 里永远是「忙」，队伍选择器一支都列不出来。`autoReturn` 的队伍碰巧没事——它的返程 leg 自己会推一条真的 `march_update`；本例五支队伍 `autoReturn` 全是 `false`，所以五支全中。主城不受影响，因为 CityScene 打开时自己重新拉一遍三片状态。

**修复①（服务端，治本）**：`processDueOccupations` 在 claim-delete 成功后调用新的 `core.pushOccupationSettled`（`core/push.ts`），发一条描述这次占领本身的 `march_update`（零距离 `occupy`／`arrived`；客户端只把它当失效信号用，不读 body）。**故意放在 claim 处而不是 `settleOccupation` 里面**：地块过期让 `settleOccupation` 提前 return、或者它整个抛异常（只记日志）时，doc 一样已经没了，客户端一样必须知道。

**修复②（客户端，兜底）**：`showTeamPicker` 在判断谁忙之前，先和 `getTeams` 并行 `refreshMarches(ctx)` 重新拉一次三片状态。push 按设计就是 best-effort（worldsvc `retries=0`，收件人不在线直接丢弃），而轮询已经没了——「玩家还能不能出兵」这个判断点不该是唯一一道防线。代价是开选择器时多一次并行往返。

**修复③（弹窗文案）**：原来四种成因共用一句 `尚无队伍，先去编辑布阵`，其中三种情况下这句话是假的。现在各说各的：拉取失败 → `world.team.loadFailed`；确实一支队伍都没编 → 原文案（此时它才是对的）；全都在行军/占领 → `world.team.allBusy`；空闲的那些都没兵 → `world.team.allNoTroops`。

**验证**：worldsvc `combatSiege-occupation-encounter-gaps.test.ts` 加 5 例（含"陈旧地块提前 return 仍要广播"、"结算抛异常仍要广播"、"claim 输给并发驱逐则不广播"）；客户端 `worldMapOccupyTeamPicker.ui.ts` 加 5 例（陈旧 occupations 不再挡住队伍 + 四条文案各一例），两边都做了 mutation 检查（去掉修复各自变红）。`client` UI 全量 2435 例、`tsc --noEmit`、`webpack` 生产构建全绿。可视化按 [[worldmap-standalone-debug-render]] 的零改源码套路（`__nwE2E.views.showWorldMap` + reject-fast stub），在真 Chrome 里逐一截图核对四条中文文案与「陈旧缓存下队伍正常列出」。

## 2026-09-02（续）：把「指令结束必须广播」做成审计——同类漏推另外还有三处

上一条修完 `settleOccupation` 之后，顺着"**任何结束一条野外指令的服务端路径都必须发 `march_update`**"这条不变量把所有同类删除点扫了一遍（`cols.{occupations,stationed}.{deleteOne,findOneAndDelete}`，共 7 处）。除已修的那处外，**另有三处真实可达的同类漏推**：

1. **驱逐（`applyOccupationExpulsion`）**——攻方打赢会删掉**原占领方**的 `OccupationDoc`，但这个方法里所有的 push 都发给赢家。被驱逐的一方**什么都收不到**：他的客户端里那条已死的占领永远留着，它点名的队伍从此一直「忙」。（顺带：他本来也无从知道自己被赶走了。）
2. **野外遭遇战打掉驻守队伍（`encounter.ts`）**——同一个 `if/else` 里，**防守方是行军**的分支早就 push 了 `march_update`；**防守方是驻扎队伍**的分支只 `deleteOne`，不吭声。结果被打掉的队伍在防守方地图上留成一个幽灵立绘，而且如果是「驻扎」模式，它在防守方的队伍选择器里永久占位。
3. **弃地（`abandonTile`）**——放弃地块会顺手释放停在上面的队伍，但客户端 `doAbandon` 只吃返回的 `me` 和重拉地块，**从不重读 `ctx.stationed`**。于是在自己「驻扎」着的地块上弃地，那支队伍在自己的选择器里也一直忙到刷新页面为止。

另外 `cancelOccupation` 同样只推 `tile_update`（目前没有客户端调用它，但路由是活的，同账号的其它设备一样会被坑）——一并补上。剩下两处（`recallStationed`、P3c 就地再派）安全：它们把队伍直接交给了一条新行军/返程 leg，那条 leg 自己会推。

**做法**：把上一条那个 `pushOccupationSettled` 泛化成 `pushOrderEnded(accountId, {tile, kind, status, at})`，五处调用点统一走它（`kind`/`status` 如实填，虽然客户端只把这条 push 当失效信号、不读 body）。

**测试分两层**：
- **行为层**：`order-end-push-sites.test.ts`（遭遇战 4 例 + 弃地 2 例，手搭 fake core，不需要 Mongo）+ `combatSiege-occupation-encounter-gaps.test.ts` 里新增驱逐 2 例、取消 2 例。每一处都做了 mutation 检查（去掉那行 push 就变红），并且都配了一条**反向**用例（防守方活下来 / 打输的驱逐 / 空地弃地 / 没有可取消的占领 → 不许广播），免得实现退化成「无条件推一发」。
- **结构层**：`order-end-push-audit.test.ts` 扫源码里所有 `cols.{occupations,stationed}.{deleteOne,findOneAndDelete}` 调用点，逐文件对照一张写明「这里为什么安全」的审查表；**新增任何删除点都会直接变红**。这层才是关键——行为测试只能覆盖有人想到的路径，而这四个洞的共同点正是没人想到。同一文件还钉住了这条规则的前提本身（客户端 `applyMarchUpdate` 会 `refreshMarches`、`applyTileUpdate` 不会），前提哪天变了应该来改这套规则，而不是绕过它。

## 2026-09-04：补两个「以为早就有、其实根本不存在」的系统——领地驻军恢复 + 队伍体力

起点是用户问「增援和设防有必要吗？我觉得领地单纯派兵驻守就够了」。逐条核代码回答那个问题时，发现用户描述的两条既有机制**在代码里都不存在**，而它们的缺失正是「增援看起来没用」的真正原因。设计落在 [`SLG_DESIGN.md` §4.6 / §5.6](SLG_DESIGN.md)，数值落在 [`BALANCE.md` §10b / §10c](BALANCE.md)；本节记排查与取舍。

**核出来的三条事实**（与用户的印象各有偏差，且偏差方向都很关键）：
1. **中立地确实「每次都打满编守军」，但机制不是 5 分钟恢复，是根本不落库**——`npcGarrison(level)` 由坐标+等级程序化推导（`combatSiege/arrival/sweep.ts`、`combatSiege/occupation.ts`），扫荡只结算掠夺和攻方伤亡。所以中立地是无状态、永远满编，比「5 分钟恢复」更硬，连那 5 分钟空窗都没有。**这一侧无需改动。**
2. **玩家领地的驻军根本不恢复**——`TileDoc.garrison` 是持久化的，全仓库只有三处写它：增援 `$inc`、围攻伤亡扣减、放弃退回兵力池。而 `shouldUseCheapSiege` 在守军为 0 时直接走线性公式，攻方零损失拿地。**一次进攻就把一块领地永久变成免费地产**，这是本轮修的主洞。
3. **「每队 100 点体力、每次 -15、每分钟 +1」这套完全不存在**——代码里的「体力」是 PvE 关卡闸门（账号级，`save.stamina`，[`BALANCE.md` §10](BALANCE.md)），不作用于行军。SLG 侧真正在限速的是别的东西：`morale`（罚**距离**，且每次出征重置为满，永不累积）、`CARD_INJURY_DURATION_MS`（5 分钟，**打光之后**才生效——用户记的那个 5 分钟大概是这个）、`SLG_TEAM_INJURY_MS`（10 分钟）、兵力池+训练时间。**没有任何机制约束出征频率**，所以一支不输的队伍可以整天连出。

**驻军恢复的核心取舍：stored / live 两个数**（详见 [`SLG_DESIGN.md` §5.6](SLG_DESIGN.md) 与 `server/shared/src/slg/garrison.ts` 的文件头）。恢复只填 stored 与等级基线之间的缺口、**永不抬高 stored**。这不是实现细节而是反刷门禁：`abandonTile` 会把 `tile.garrison` 退回兵力池，若恢复写进 stored，「占一块 10 级地（付 `GARRISON_PER_TILE`=500）→ 等 5 分钟 → 放弃退 1200」就是无限兵力龙头。**运气好的是既有代码本来就把伤亡当作增量打在 stored 上**（`landSiege.ts` 2026-08-24 那次「反盲写」改造留下的形状），所以这条性质是白拿的——伤亡可以超过 stored 并被夹到 0，即恢复出的民兵能战死但永远无法提现。相应地 `reinforce` **刻意不动 `garrisonRegenAt`**：被打残后立刻增援不会清零已积累的恢复进度。基线取 `npcGarrison(level)`（=「它作为中立地时的守军」）而不是 `GARRISON_PER_TILE`，因为前者是代码里唯一**由格子本身推导**的守军数——占领写 500、围攻胜写攻方残兵、倒计时结算写 `contestedGarrison`，同一块地有三个不同历史值，只有等级基线让「这块地会用多少兵抵抗」与归属无关。

**「缺检查点 = 已在基线」这个默认值是有代价的**：它是历史 TileDoc 的迁移路径（否则老地永远停在 0，而 0 就是白送），但代价是**所有建立/战损写入都必须盖 `garrisonRegenAt` 时间戳**，否则刚打下来的地会读成「瞬间满血」。四处写入点全部补了：`territory.ts` 直接占领、`occupationSettle.ts` 倒计时结算、`combatSiege/damage.ts` 建筑易手、`core/spawn.ts` 出生。

**队伍体力的两个刻意留的口子**：①**散兵行军（`reinforce`/`sweep`）不计费**——它们不挂队伍，没有预算可扣，而且这是有意的：让「五队都累了」的玩家仍有事可做，而不是把整张世界地图锁死；回收这个口子要连着散兵行军一起重做。②**不做付费补充**——它是频率闸门，可付费绕过就等于没有（与 PvE 体力刻意不同，那个可以 30 金币 +60）。**忙碌优先于体力**：两者同时成立时报 `TEAM_BUSY`（该做的是召回）而不是 `TEAM_EXHAUSTED`（该做的是等）——这条有专门测试钉住，因为反过来会把玩家引向一个解决不了问题的动作。并发上不加乐观锁是有依据的：`marches` 上 `{worldId,ownerId,teamId}` 的 partial-unique 索引保证一支队伍同时只有一条活指令，而 `startMarch` 是唯一消费者；这条前提写进了代码注释，**将来加第二个消费者必须比照兵力池的 `$gte` 原子过滤改写**。

**两处既有测试被这次改动改了断言，都不是「改到测试通过」而是原断言的前提真的变了**：
- `teams.e2e.test.ts` 那条「card-army dispatch 对 `playerWorld` 一个字都不写」——现在会写 `teamState.<id>.{stamina,staminaAt}`。它真正要守的性质（并发结算不被覆盖、不报 `REV_CONFLICT`）没变，因为这是两个 scoped dotted path 的 `$set`，天然可交换；并且按 `command.ts` 里既有的那段推理（`rev` 是纯乐观锁、无业务含义），这次的写入**同样不 bump `rev`**——所以 `rev` 断言反而一个字没改，只补了一条断言体力确实扣了。
- `siege-replay-cardinstances.e2e.test.ts` 那条「弱守军，卡牌队应该干净取胜」——目标格选取原先不限等级，恢复上线后到达时它站在 `120 × 等级` 的基线上，最高档就是 1200，于是「弱守军」变强、断言翻成 `defender_win`。改法是把目标格钉到 1 级（基线 120 ≈ 原本想表达的 100），让这条用例继续考它该考的（replay 保真度），而不是考恢复曲线。

**验证**：`server/shared/test/garrison.test.ts`（14 例，两条曲线的上下限/「超额不动」/时钟回退）；`server/worldsvc/test/core-helpers-gaps.test.ts`（+8 例 `liveGarrison`：按等级恢复、缺检查点=在基线、超额原样、未占领/主城/ring 三类不恢复）；`server/worldsvc/test/combatMarch-command-branch-gaps.test.ts`（+8 例体力：从未出征=满额、按**回复后**的值扣费、边界 15 可出征/14 拒、失败 dispatch 不扣费、停留再出征照扣、散兵不扣、忙碌优先）。契约改动走 codegen（`gen-openapi-world.mjs` + client `rest:gen`），未手改生成物。
